# MiniKV 设计

## 产品契约

MiniKV 是用 Go 构建的单实例内存键值缓存，面向回源昂贵、可以重建的数据。以商品详情页为例，应用将商品描述、图片列表和聚合结果序列化成字节，存入 `product:42:detail`。缓存命中可以省去数据库和搜索服务的查询。库存扣减、支付幂等和会话撤销等权威状态由业务系统保存。

`SET` 成功表示新值和截止时间已在单个键上原子发布。MiniKV 在回包前完成发布，其后的读取根据当时的状态判断是否命中。TTL 从发布时起算，限定新读取可以选中这个值的最晚时间。访问命中时保持原截止时间。实际驻留时间可能更短，替换、删除、内存淘汰和进程重启都可以让它提前消失。实例重启后从空缓存开始，应用负责回源。

| 操作结果 | 应用可依赖的行为 |
| --- | --- |
| `GET` 命中 | 返回本次读取选中的完整值。读取选中后，即使该值在响应发完前到期或被淘汰，本次响应仍可发完。 |
| `GET` 未命中 | 键缺失或已到截止时间。两种情况都返回未命中，应用按自己的限流和超时策略回源。 |
| `SET` 明确拒绝 | 此次写入未发布，也未淘汰其他条目。若原值在读时仍有效且未被其他操作修改或移除，读者仍得到原值，沿用原截止时间。原值到期后返回未命中。 |
| 过载或连接超时 | 过载与未命中是不同结果，调用方按过载处理。已发出的写请求若超时且未收到结果，提交结果未知。 |

## 商品详情读取和回填

1. **查缓存。** 应用用 `GET` 查询 `product:42:detail`。连接处理器解析键并按哈希路由。目标分片在读锁内查找条目，读取单调时钟并判断截止时间。命中时先预留发送额度，再带着不可变值的引用释放读锁。网络发送在锁外完成。
2. **回源。** 到期或缺失时，应用在自己的回源预算内查询商品数据。查到结果后即可返回给用户，并尝试带 TTL 回填。MiniKV 只处理键和值，回填能否落入缓存独立于这次业务请求能否成功。
3. **提交回填。** 应用使用 `SET` 的仅未命中写入选项。在目标分片的写锁内以当前截止时间重新检查键。如果另一个请求已回填有效值，本次保留该值并返回已存在。显式覆盖同样校验容量，成功时一起更新值和截止时间。
4. **容量不足。** 分片有可用空间时直接接纳。需要腾空间时，先在有界的候选集合内挑已过期条目，再挑写入时间较早的有效条目。目标键排除在候选之外，覆盖按新旧条目的净增量计算。先算清可腾出的字节和槽位，足够时才一次提交淘汰和写入。对象超限、在途额度用尽或本轮凑不够空间时，明确拒绝回填。

仅未命中写入解决两个请求同时回填时互相覆盖的问题。商品源数据若在回源期间更新，应用仍需按业务新鲜度选择 TTL。要求按源版本读取的场景可以把商品版本放进缓存键。

## 分片索引与过期回收

| 部分 | 职责 |
| --- | --- |
| 连接处理 | 限定连接数、键值大小、请求和响应的在途字节，处理读写超时。 |
| 数据分片 | 用同一把读写锁协调键索引、条目、截止时间、淘汰和容量记账。 |
| 后台回收 | 轮流扫描分片中的少量槽位，在分片写锁内按当前截止时间回收。 |

每个分片用 `map[string]uint32` 将键映射到紧凑的条目数组。条目保存键引用、不可变字节值、单调时钟截止时间和写入顺序。索引和条目共享同一份键字节。值使用缓存独占的字节数组，连接解析缓冲可独立复用。删除时将末尾条目移到空位，更新对应索引并清空原来的末尾槽。数组多一次间接访问，换来固定成本的抽样和可续扫的回收位置。

命中路径的成本来自路由哈希、查表、槽位读取、时钟判断、读锁和出站额度记账。命中以无额外堆分配为目标。按写入顺序淘汰，读取路径省去访问顺序更新。单个热点键及同分片写入仍会竞争，压测需要区分读锁等待、共享额度竞争与网络发送耗时。

写入在收取键和值前先校验声明长度、预留入站额度，并在锁外准备独占缓冲。写锁内只做状态复查、候选选择和提交。预设每分片的条目数和字节额度，按条目数预留槽位和索引空间。固定额度省去跨分片协调，代价是个别分片可能在实例总体尚有余量时开始淘汰。分片级占用和淘汰次数用于识别这种偏斜。Go map 的容量提示用于减少扩容，仍要测量索引峰值和扩容时的持锁时间。[Dragonfly 分片架构](https://github.com/dragonflydb/dragonfly/blob/main/docs/df-share-nothing.md)

到期判断以进程内单调时钟为准，`now >= deadline` 时返回未命中。后台使用同一个条目数组分批清理，每批限制扫描和删除数量。拿到写锁后重新读取当前截止时间，保护刚被覆盖的条目。集中到期时，回收可延后，过期但尚未移除的条目继续占用容量。这样可以用有界的清理工作换取短持锁时间，同时维持读取的截止时间契约。[Redis 主动和被动过期](https://redis.io/docs/latest/commands/expire/#how-redis-expires-keys) · [Go 单调时钟](https://pkg.go.dev/time#hdr-Monotonic_Clocks)

## 容量记账与慢客户端

**从索引移除一个值，只归还缓存条目额度。** 比如一个慢连接持有 4 KiB 的商品详情，发送还在阻塞，另一笔写入已淘汰该键。这时新 `GET` 会未命中，槽位可复用，旧值仍被发送方引用。发送结束或中止、处理器释放最后一个引用后，旧值的底层数组才可由 GC 回收。已经交给内核的字节可能还留在 socket 缓冲区。

| 预算 | 计入内容及释放时点 |
| --- | --- |
| 缓存条目 | 计入仍在索引中的键和值的分配容量，以及预留的索引、槽位和元数据空间。删除归还该条目的键值额度和可复用槽位。 |
| 入站 | 在读取请求体前，按预计分配容量预留各连接及全实例的在途额度。提交时先记入条目额度，再移交缓冲并归还入站额度。请求中止或写入被拒绝时，处理器在释放缓冲后归还额度。 |
| 出站 | 在读锁内、值引用离开分片前，按整个底层值的计费容量预留各连接及全实例额度。值已驻留时仍预留，同一个值发给多个连接时按响应分别预留。实际响应缓冲也计入预算。发送方放弃引用后才归还额度。 |

按响应预留会保守地重复计算共享值，代价是热门大值可能提前触发过载，收益是淘汰时无需追踪每个值还有多少读者。额度申请有界，失败后释放已取得的额度和分片锁，再返回过载。每连接串行处理请求，最多保留一个待发送响应。响应使用覆盖完整发送过程的写截止时间，慢速发送无法持续延长它。截止后关闭连接并释放引用。连接数和固定连接缓冲也有上限，过载回包使用其中预留的小缓冲。

缓存额度与入站、出站额度之和是应用侧容量规划的起点。替换时旧值与待写入值可能同时占用内存，删除后 GC 和页回收也需要时间。进程预算还要给分配器取整、索引增长、堆留量、连接栈和运行时预留空间。部署上限另外考虑内核网络缓冲。`GOMEMLIMIT` 用于引导 Go 控制内存，是软限制。高频分配时，写请求可能需要协助 GC 标记，并通过 CPU 竞争或较长持锁影响读取尾延迟。[Go GC 指南](https://go.dev/doc/gc-guide)

| 表现 | 优先核对 |
| --- | --- |
| 缓存额度接近上限，满载写入频繁淘汰或拒绝 | 看各分片条目字节、槽位占用、回收速率和采样得到的过期滞留。出站占用稳定时，优先检查工作集大小、清理积压和分片偏斜。 |
| 缓存条目占用回落或趋稳，发送仍然积压 | 分别看值引用的出站预留、编码缓冲字节、写阻塞时长和写超时，再结合内核 socket 占用定位排队位置。在 Linux cgroup v2 部署上可看 `memory.stat` 的 `sock`。 |
| 条目和在途额度稳定，RSS 或尾延迟上升 | 对比分配速率、堆存活量、扫描字节、GC assist 和锁等待。额度回落后堆占用、RSS 可以延迟下降。分配与 assist 同时上升时，用运行时跟踪确认延迟落在哪段路径。 |

容量额度是保守的记账值，RSS、堆和 socket 内存应各自采集，避免把可共享的预留和真实占用直接相加。[Go 运行时指标](https://pkg.go.dev/runtime/metrics) · [Linux cgroup v2 内存指标](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory)

验收时用可控的阻塞发送器暂停一个已持有旧值的响应，再用另一笔写入淘汰该键。检查新读取未命中、缓存额度先归还、出站额度在发送结束或超时后归还。把淘汰替换为一次空间不足的覆盖，检查明确拒绝后仍能在原 TTL 内读到旧值。

## 缓存接近满载，冷数据扫描后又发生热点迁移

**实验设置。** 两组使用相同总内存和进程上限，过滤器也计入预算。用同一批商品详情预热到缓存预算的 95% 以上，以固定到达速率持续读取热点，同时扫过累计约为缓存容量两倍的一次性冷数据。扫描结束后切换到新的热点集合。两组复用同一请求序列、对象大小分布、回源预算和超时，TTL 长于实验窗口以集中观察容量效应。

**直接接纳。** 每次未命中回填只要能在相同的工作量内腾够空间，就提交。容量不足时沿用先过期、再按抽样中的写入顺序淘汰的策略。

**回填准入。** 仅未命中回填且必须淘汰仍有效的条目时，查询该分片按时间窗口轮换的固定大小近似过滤器。第一次尝试只标记该键的哈希位置，明确返回未缓存。窗口内再次尝试时，才用同一套候选提交。剩余空间或过期条目已足够时直接接纳。过滤器的误判可能让少量一次性键提前进入，新热点则可能多回源一次。[TinyLFU 准入思路](https://arxiv.org/abs/1512.00727)

**实验预期。** 准入应减少扫描期间已有热点的回源次数，但会推迟新热点进缓存。按扫描期和迁移期分别记录后端实际执行的查询次数、CPU 时间、超时和拒绝数，同时比较业务请求 P99 和缓存 `GET` P99.9。预热时间从切换热点起算，到对新热点的命中率连续三个 10 秒窗口达到 95% 为止，未达标则记为未完成。

**取舍判据。** 建议的门槛是扫描期旧热点回源至少减少 30%，两个阶段合计的后端实际工作量下降，业务成功率至少持平，业务请求 P99 和缓存 `GET` P99.9 在任一阶段的恶化均在 5% 以内，新热点预热时间增加在 10% 以内。达不到这些门槛，或收益在代表性业务请求序列上无法复现，就保留直接接纳。

**实测结果。** 相同内存和并发下，两次回填减少了扫描期旧热点的回源。热点迁移时，在线 P99 增加 11.3%，缓存 GET P99.9 增加 13.2%，新热点预热从 30 秒延长至 40 秒，均超过对应退化上限。服务保留直接接纳。[并发对照](admission.md#并发对照)
