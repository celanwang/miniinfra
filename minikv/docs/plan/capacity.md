# 默认分片的延迟与容量

## 环境与口径

MiniKV 使用 16 分片、每片 4 MiB 和 4096 槽，直接接纳，每次写入最多检查 16 个淘汰候选。实验入口复用 TCP 服务及默认连接配置，增加一个独立的本地诊断端口和 10 ms 出站额度采样。Redis 使用 7.4.12、64 MiB `maxmemory`、`allkeys-lru`、单 I/O 线程，关闭快照和 AOF。每行使用新容器。服务有相同的 2 CPU 配额、160 MiB 内存硬上限和禁用额外交换空间的设置。客户端单独分配 4 CPU、256 MiB，通过共享网络命名空间访问服务的 Linux 回环地址。

两组采用同一组键值、计划请求序列和 96 条连接，每连接流水线深度为 1。只对照普通 `GET` 和无期限 `SET`。MiniKV 的 64 MiB 按分片记账，Redis 的 64 MiB 按实例执行淘汰，内存统计口径、淘汰语义、数据表示和线协议均有差异。这里对照的是配置与负载确定时的服务表现。 [Redis 淘汰](https://redis.io/docs/latest/develop/reference/eviction/) · [Redis 流水线](https://redis.io/docs/latest/develop/using-commands/pipelining/)

两组的 TCP 自动发送缓冲上限均设为 128 KiB，后台客户端的接收缓冲请求值为 64 KiB。这个设置使暂停读取 1 MiB 值的连接能在服务端形成背压。客户端和容器间的网络条件也因此属于结果的一部分。 [Linux TCP 缓冲](https://docs.kernel.org/networking/ip-sysctl.html#tcp-wmem)

## 负载与复现

普通组用 88 条连接。预热 2048 个 512 B 小值及两个 1 MiB 大值。普通组约 80% 的请求落在 8 个热点键，约 5% 是覆盖写。后台组有 8 条连接和 40 个请求/秒，三个场景各自重启服务。

| 场景 | 后台请求 |
| --- | --- |
| 小值 | 小值读和覆盖写，作为普通读写基线。 |
| 混合 | 两个大键，约九成 GET 和一成覆盖 SET，客户端立即读取响应。 |
| 慢读 | 与混合场景使用同一序列。后台 GET 写完请求后等待 120 ms，再读取响应。 |

负载发生器每 1 ms 按目标速率放入计划请求，普通组队列最多 256 个待派发请求，后台组最多 8 个。队列满计为 `Waiting`，调度器迟于计划节拍超过 5 ms 计为 `Late`。两项都占用计划请求的分母。实际发送以完整请求写入 TCP 为准。普通小值命中从计划时刻计到完整响应读完，另报从实际开始发送计时的 RTT。退出和超时按同一个 1 秒客户端期限统计。进程 RSS 和高水位来自 Linux 的 `/proc/1/status`。服务 CPU 取同一进程的用户态与内核态 CPU 计数差。

容量试验单独运行。以 32 条连接写入 100000 个不同的 1 KiB 值，再以 8 条连接提交 256 个不同的 1 MiB 值。记录两组写入结果和 MiniKV 16 个分片的回收及拒绝计数差。并发连接之间的实际执行顺序由服务调度决定。

在组件目录运行以下命令。需要 Go、Python 3、Docker 和本地 `redis:7-alpine` 镜像。每行 JSON 包含计划量、发送量、响应分类、命中样本量、RSS 和 MiniKV 分片诊断。下列默认阶梯每档计划发压 6 秒。

```sh
python3 experiments/capacity.py
```

**少量慢读。** 1 ms 下有尾延迟波动，例如 MiniKV 在 100k/s 的慢读 P99.9 为 18.53 ms，混合为 7.46 ms。250 µs 下同档小值、混合、慢读的 P99 分别为 3.56、3.53、3.56 ms，P99.9 分别为 5.22、4.78、4.90 ms。60k/s 与 150k/s 也没有一致的慢读退化。慢读确实将 MiniKV 采样出站峰值从混合的约 1 MiB 推至约 5–6 MiB，仍低于默认 32 MiB 额度。此处的结论适用于 8 条后台连接、40 请求/秒和 120 ms 的暂停。

**过载区间。** 以超过 1% 的计划请求未完成作为本实验的提示线。MiniKV 在 1 ms 下 60k/s 已有 0.55%–1.52% 损失，100k/s 增至 8.01%–14.49%。250 µs 下三种负载到 100k/s 都完成 99% 以上，150k/s 降至 91.49%–92.46%，实际约 137.2–138.7k/s。Redis 在相同节拍也出现类似区间。可以定位这套 TCP 回放的过载区间在 100k–150k/s。缩短节拍明显改变了发送率，未发主要发生在客户端有界队列。服务在 150k/s 的 6 秒里最多消耗约 2.4 CPU 秒，发压器最多消耗约 8.3 CPU 秒。平均 CPU 仍有余量，队列积压也可能同时受 TCP 等待和调度影响，因此无法据此确定服务独立的吞吐上限。高档位更短的尾延迟只描述已成功的样本。

## 近满写入与进程内存

| 服务和运行配置 | 1 KiB 预填 | 256 次 1 MiB 写入 | 进程 RSS |
| --- | --- | --- | --- |
| MiniKV，默认 Go 内存设置 | 两次定位复跑均完成 100000 次 | 三轮被 cgroup OOM 终止。两次定位复跑均在预填完成后终止 | 以 160 MiB cgroup 硬限制的 OOM 事件判定 |
| MiniKV，`GOMEMLIMIT=112MiB` | 两轮均完成 100000 次 | 两轮均返回 256 次 `NO_SPACE`，`BUSY` 和超时为 0 | 两轮结束为 107.0、109.0 MiB，峰值为 128.6、113.2 MiB |
| Redis，64 MiB `maxmemory` | 全部成功 | 每轮均接受 256 次写入 | 峰值 124.9–126.7 MiB |

MiniKV 的两个软限制对照里，每个分片预填后均有 3612 条，记账 4193560 字节，剩余 744 字节。16 个采样候选最多腾出 16544 字节，无法满足一笔 1 MiB 插入。因此这批 `NO_SPACE` 是有界淘汰的结果，两轮合计回收增量都为 0。Redis 能从整个实例淘汰大量小值来接纳大写，写入成功反映了不同的淘汰契约。

| 分片 | 第一次软限制对照的 `NO_SPACE` | 第二次软限制对照的 `NO_SPACE` |
| --- | --- | --- |
| 0–7，依次 | 21, 19, 9, 11, 18, 18, 17, 12 | 16, 16, 16, 23, 11, 15, 13, 17 |
| 8–15，依次 | 19, 13, 11, 15, 20, 16, 17, 20 | 20, 18, 19, 10, 18, 16, 14, 14 |

MiniKV 先按网络额度收齐写入体，再裁决分片容量。即使写入后续被拒，准备这些值仍产生短期分配。64 MiB 缓存额度约束条目，部署还需要给运行时、内核与在途数据留出余量。对于这里的 160 MiB 容器，112 MiB 软限制在两轮中让实例存活并返回其完整的容量结果。这个设置是本实验的对照值，软限制的延迟和 CPU 代价尚需随部署负载验证。 [Go GC 内存限制](https://go.dev/doc/gc-guide#Memory_limit)

```sh
python3 experiments/capacity.py --profiles capacity
python3 experiments/capacity.py --profiles capacity --go-memory-limit 112MiB
```

## 近满写入并发小读

沿用 64 MiB 缓存、160 MiB cgroup 上限、100000 个 1 KiB 预填、8 条连接提交 256 次 1 MiB 写入。预填后放入 16 个 512 B 热键，16 条小读连接按 10k/s 计划速率回放 2 秒。大值写在小读开始约 250 ms 后发起。P99 按请求的计划时点分为写入前、写入期间和写入后，仅统计完整命中，未发和失败另计。每条写连接的最后一次请求结束后，在同一连接读一个热键以校验协议恢复。

Go 1.27.3，Linux arm64 Docker，服务固定在 CPU 0–1，驱动固定在 CPU 2–5，各自仍受 2 和 4 CPU 配额限制。旧实现取自 `03d0905`。默认 Go 设置下旧实现与缓冲复用版本交替先后顺序，共三对，每次用新容器，串行运行。旧实现的 112 MiB 软限制对照独立跑三轮，采用相同固定 CPU 与协议负载。启动时同一 Docker 引擎没有其他运行容器。宿主调度仍共享，这里的尾延迟只用于比较本次负载。cgroup 和运行时计数从隔离容器内采样，RSS 来自 Linux 进程状态，失败组的峰值取退出前能采到的值，OOM 由 Docker 状态确认。累计分配、GC 与 CPU 的差值使用写入前后快照。

软限制对照和缓冲复用版本每轮完成全部 20000 次小读，`BUSY`、超时和连接错误为 0。缓冲复用版本每轮写入期间有 1792–2100 个小值命中，软限制对照有 2877–3150 个。旧实现的 155–200 个大写连接错误出现在实例退出期间，成功小读的延迟样本只代表退出前的一部分请求。

在途入站峰值约 8 MiB，旧实现仍会为每次被拒的请求分配一个临时值。这里主要耗尽的是重复分配与垃圾回收之间的堆余量。软限制通过更频繁的回收让实例存活。复用精确长度的未发布缓冲使写入窗口的中位分配下降约 97%，保留了原容量结果和帧边界。代价是默认最多持有 8 MiB 空闲缓冲。写入期间的小读 P99 中位数为 11.92 ms，软限制对照为 11.88 ms。这两组的峰值 RSS 区间重叠。本轮保留显式配置运行时软限制的部署能力，并使用有界复用降低本场景的分配压力。

在各版本的组件目录运行。两组命令分别从 `03d0905` 和含缓冲复用的版本构建服务与驱动。依次运行，避免同一宿主的两个实验竞争。

```sh
python3 experiments/capacity.py --profiles pressure --server-cpus 0-1 --driver-cpus 2-5
python3 experiments/capacity.py --profiles pressure --server-cpus 0-1 --driver-cpus 2-5 --go-memory-limit 112MiB
```

### 按接收容量复用

64 KiB 及以上的大值按 4 KiB 取整接收，申请实际接收容量的在途额度。额度或单值上限不足时回退至精确长度。只有通过分片裁决的写入才会发布。精确容量的缓冲可直接交给条目，取整缓冲在写锁内复制出精确容量的值，原缓冲继续受空闲池上限约束。被拒写入既不用复制，也不会改变现有条目。

以 `52114c0` 的精确长度版本为对照。同一驱动，在固定 CPU、160 MiB 硬上限和默认 Go 内存设置下，各做三对交替顺序的回放。取整版本每一轮都返回 256 个 `NO_SPACE`，完成 20000 次小读，且 8 条写连接都能继续读。表中分配统计写入前后的累计分配差，中位数和 P99 只取完整轮。

| --- | ---: | ---: | ---: | ---: | ---: |
| 固定 1 MiB | 0/3 | 0/3 | 8.40 / 8.50 | 10.06 / 10.42 ms | 118.0–128.1 |
| 四种轮换 | 1/3 | 0/3 | 33.06 / 22.41 | 11.52 / 11.03 ms | 127.2–139.0 |

### 成功大写的代价

### 同分片覆盖对照

本轮将 256 次大写集中到一个现存键。16 条小读连接平均分组，各读 8 个已预热的 512 B 键。一组使用写入所在分片，另一组使用相邻分片，两组分别收到同一计划速率的半数请求。测试入口提供实际分片映射，发压器按映射选键。服务与驱动仍各自固定在 CPU 0–1 与 2–5，使用相同的 160 MiB 硬上限、2 秒小读计划及默认 Go 内存设置。每轮使用新容器，串行、交替顺序运行。正式对照每轮开始前均无其他运行中的 Docker 容器，宿主调度仍可能引入波动。

先比较现有服务的 `publish-locality`（1 MiB 少 1 字节，锁内复制）与 `publish-aligned`（1 MiB，接收缓冲直接移交）。三对普通回放中，写 P99 中位数为 11.58 和 13.82 ms，同分片小读 P99 中位数为 13.70 和 14.54 ms，跨分片为 13.41 和 14.46 ms。对齐的一轮有 5 个调度晚发。普通端到端数据未复现先前双写键实验的写 P99 排序。

带阻塞采样的独立轮次记录到局部成本。两次未对齐验收分别采到 79 和 103 次 `Store.Get` 的读锁阻塞，累计阻塞约 20.5 和 20.6 ms。对齐控制未采到该调用栈。这个对照通常同时移除了锁内分配和复制，采样能定位等待发生的位置，尚无法拆出分配、复制和调度各自的耗时。阻塞采样轮次用于归因，下面的 TCP 延迟来自关闭采样的回放。

**候选方案。** 在读取值体前，对非 NX 等容量覆盖做一次读锁检查。命中时使用精确接收缓冲，按实际容量调整入站额度，读完值体后照常在写锁内检查当前状态并发布。这样能移除这一类覆盖的锁内复制，已有条目或容量的后续变化仍由原有路径裁决。未通过裁决的完整帧仍返回对应响应，缓冲归还遵守原额度。

| 指标，五对普通回放的中位数 | 现有锁内复制 | 直接精确接收候选 |
| --- | ---: | ---: |
| 成功 SET P99 | 12.32 ms | 14.69 ms |
| 同分片小读 P99 | 13.96 ms | 14.04 ms |
| 跨分片小读 P99 | 12.87 ms | 14.08 ms |
| 同分片小读 RTT P99 | 10.27 ms | 10.51 ms |
| 跨分片小读 RTT P99 | 10.01 ms | 10.63 ms |
| 写窗口累计分配 | 263.94 MiB | 256.77 MiB |
| 写窗口 cgroup CPU | 58.75 ms | 56.27 ms |
| cgroup 峰值 | 45.71 MiB | 37.31 MiB |
| 进程 RSS 峰值 | 50.72 MiB | 42.99 MiB |
| 空闲接收缓冲峰值 | 8 MiB | 1 MiB |

每轮均成功完成 256 次覆盖，8 条写连接随后都能读取。每轮计划 20000 次小读，全部已发小读成功。候选的一轮有 7 次调度晚发，其余轮均完整发出。写入期间每组每轮有 930–1570 个小读样本。现有路径与候选的 SET P99 区间分别为 9.30–16.74 ms 和 12.13–19.08 ms，候选在五对中有四对更高。同分片小读无稳定收益，两组小读的高点常同时出现在同一轮。

另做两对带阻塞采样的比较，现有服务分别记录 63 和 77 次 `Store.Get` 读锁阻塞，累计 16.6 和 124.1 ms。候选两轮均未采到该栈。固定、轮换和相邻互异的近满拒写回归各做两对，两侧均为每轮 256 个 `NO_SPACE`、20000 次小读完成、8 条连接可继续读，且 OOM 为 0。候选的专项竞态测试验证了旧响应不可变、读取值体期间容量变化后重新裁决，以及拒绝后原连接仍能读取。仓库的条件写入口为 `SET NX`。

**保留现有实现。** 候选减少了采样中的读锁等待和这一成功覆盖场景的峰值内存，端到端小读收益欠稳定，写 P99 也偏高。保留实验补丁，以便用相同驱动验证这项取舍。下一步优先用执行跟踪分开计量网络收发、goroutine 唤醒和发布等待，解释同分片与跨分片尾延迟为什么同时变化。

### 空闲池跨尺寸切换

空闲池的旧策略在仍有空间时才接受归还。白盒测试把 8 MiB 填满于单个尺寸，再归还另一尺寸，两个方向都会丢掉新缓冲。后续该尺寸即使反复出现，也不会获得可复用的槽位。

沿用默认 16 分片、64 MiB 缓存、160 MiB cgroup 硬上限和默认 Go 内存设置。预填 100000 个 1 KiB 小值，再由 16 条连接按 10k/s 计划速率发出 20000 次小读。第一阶段使用正常 TCP SET，将每条值体保留最后一字节，等所有请求取得入站额度再发送最后一字节。1 MiB 用 8 条连接，512 KiB 用 16 条。两组保持同一进程，结束时确认空闲池确实占满 8 MiB。随后用 8 条连接发出 256 MiB 的另一尺寸写入。冷启动对照从相同的新进程预填后跳过第一阶段。

### 宽尺寸混合回放

这轮用一个合成业务回放验收尺寸替换后的部署边界。沿用 16 分片、64 MiB 缓存、160 MiB cgroup 上限、2 CPU 服务和 4 CPU 驱动。服务器固定 CPU 0–1，驱动固定 CPU 2–5。使用 Linux arm64 Docker 和 Go 1.27.3。每轮启动前等待其他 Docker 容器结束，每对交换先跑顺序，宿主调度仍共享。

预填 100000 个 1 KiB 值时保留一个分片给覆盖写。其他分片逼近容量上限，正式写入前的缓存记账为 62.62 MiB。16 条小读连接在 2 秒内计划发送 20000 次热点 512 B GET。8 条写连接提交 512 次 SET，每四次写约有一次覆盖已有键，其余尝试向近满分片插入。覆盖使用 512 B 至接近 1 MiB 的 15 种长度，共约 35.02 MiB 值体。插入使用 64 KiB 至 1 MiB 的 10 种长度，共约 160.25 MiB，后半段中大值更密集。键按各实例的实际分片路由选择。驱动逐笔检查 `STORED` 与 `NO_SPACE`，结束时通过原连接逐字节核验 8 个最新值。

### TTL 集中与散开到期

用默认的 16 分片和 65,536 槽做槽位满载对照。通过实验入口读取键的实际分片映射，每分片预填 4096 个 512 B 值，其中 2048 个带 TTL。集中组在同一时点附近到期，散开组将同样数量拆成间隔 200 ms 的 16 批，跨度 3 秒。统一将首批目标到期时刻记为 T。每次 SET 在回包前完成发布，因此驱动用“收到回包的时刻加上送出的 TTL”为到期上界。探测在该上界之后发出。确定性存储测试另行确认了键仍占槽时，到期 GET 已返回未命中，后续清扫才归还槽位和键值额度。

两组都在 T 前 400 ms 开始，由 16 条连接以 10k/s 计划速率读 5 秒热点非过期键。T 前覆盖 16 个将到期的键。T + 40 ms 起，在各分片用 NX 插入 4 个新键。另选每分片一个到期键，两条连接发起同键 NX，核对一个 `STORED`、一个 `EXISTS`，并读回胜出值。按各自到期上界检查其他 128 个到期键，在 T + 6.2 s 再读覆盖值和 NX 胜出值。容量监测只采集现有分片计数，每 200 ms 取样一次，包含写入和后台清扫带来的回收。待回收下界用到期上界已过的键数，保守减去所有已计回收、活键淘汰和最多 16 次原位 NX 替换。

验收要求三对回放无到期后命中、覆盖丢失或错误的 NX 胜出结果，64 次新键回填全部成功，已发热点小读全命中，计划完成率至少 99.5%。热点 GET P99 比较同一个 T − 50 ms 至 T + 500 ms 窗口。若集中到期在三对里均使该窗口 P99 增加至少 2 ms 且超过 50%，继续定位可复现的前台影响。后台计数单独记录。服务固定 CPU 0–1，发压器固定 CPU 2–5，同一 160 MiB 容器上限和 Go 默认内存设置，三对串行并交换顺序。每轮启动前等待其他 Docker 容器结束，宿主调度仍共享。

### 字节近满时的 64 KiB 回填

沿用上面的 TCP 回放环境和 10k/s 热点读。两组每分片都接近 4 MiB，每片有一个相同的 512 B 热点键，约四分之三的填充值集中到期。回填对象都是 64 KiB，含键记账 65,545 B。两组的差异是每个旧条目能归还多少字节。

| 组别 | 每片预填条目 | 普通旧值 / 条目记账 | 初始空闲 | 16 个候选最多归还 | 初始空闲时需要的旧条目 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `byte-fit` | 512 | 7,300 / 7,309 B | 132 B | 116,944 B | 9 |
| `byte-limit` | 1,024 | 3,642 / 3,651 B | 58 B | 58,416 B | 18 |

每片在到期前覆盖一个键并清除其 TTL。到期上界之后，每片访问一个新的回填键三次，首访在上界加 1 ms 后启动，后两次目标为上界加 30 和 120 ms。每次先 GET，未命中时实际生成一份 64 KiB 模拟回源值并发出 `SET NX`。同一个键再次回源计为额外工作。热点小读结束后验证原到期键不可见、覆盖值仍在且受 NX 保护，再读回新值核对内容。

每波请求前后采样各分片的记账与回收计数。首次回填前的已到期可回收字节由尚未回收的到期条目数乘以条目记账算出。`byte-fit` 未清扫时，首个 16 槽候选窗内有 11 个到期条目，足以回填。如果某分片返回 `NO_SPACE` 且波后空闲加上 16 个旧条目的上界仍小于 65,545 B，该次拒绝在候选数约束下不可避免。若前后采样夹住了阈值，只能知道两次采样间归还了额度。每个分片在单波内只有一次回填机会，因此拒绝所在分片在这段时间内只有清扫可以改变可用空间。

```sh
GOWORK=off python3 experiments/capacity.py --profiles ttl --ttl-pattern byte-fit \
    --server-cpus 0-1 --driver-cpus 2-5
GOWORK=off python3 experiments/capacity.py --profiles ttl --ttl-pattern byte-limit \
    --server-cpus 0-1 --driver-cpus 2-5
```

**实测。** 同一 160 MiB 容器硬上限下串行运行三对，交换先后顺序。首次拒绝所在分片在波前均有约 2.67 MiB 已到期且仍占用的字节。`byte-fit` 的 48 次首次回填全部成功，其中 37 次波前尚无清扫回收，波后只回收了 9 个到期条目。`byte-limit` 的 57 次拒绝中，52 次在波后仍凑不满 65,545 B，其余 5 次的采样夹住了总额跨过阈值的时点。所有拒绝的波前空闲加上候选字节上界均小于 65,545 B。

| 每轮指标 | `byte-fit` | `byte-limit` |
| --- | ---: | ---: |
| 首访回填成功 / 16 | 16 | 3–5 |
| 首访 / 第二波 `NO_SPACE` | 0 / 0 | 11–13 / 6–7 |
| 三波内总回源 / 额外回源 | 16 / 0 | 34–36 / 18–20 |
| 第三波结束可读到正确新值 / 16 | 16 | 16 |
| 活键淘汰 | 0 | 0 |
| 热点 GET 计划时刻至读完 P99，中位数（范围） | 4.58 ms（4.42–4.60） | 4.68 ms（4.60–4.70） |
| 同窗口热点 GET RTT P99 范围 | 0.10–0.20 ms | 0.10–2.60 ms |

六轮的覆盖值都保留，原到期键都返回 `MISS`。已发送的热点 GET 全命中，完成计划请求的 99.89%–100%。热点 P99 窗口沿用前一实验。两组的计划时刻至读完 P99 配对差值最大 0.28 ms。回源计数衡量本地模拟工作量，这里没有测量真实后端的请求耗时。

**保留 16 个候选与定额清扫。** 分片已有足够的到期字节，仍可能因单次 SET 能移除的条目数有限而拒绝回填。已知边界下，换一组同大小候选也凑不满预算。可凑足的对照组在当前布局下当场成功，两个组的热点均保留。这组数据把 `NO_SPACE` 的前台代价界定为等待清扫期间的额外回源，支持在现有工作量上限内维持实现。该结论适用于本实验的 64 KiB 回填及均匀交错的过期条目，零散分布或多键同时争用同一分片会改变候选及空闲字节。

## 小 GET 响应发送

逐段写先发 `VALUE` 头，再发非空值。对照用 `net.Buffers.WriteTo`，在 Linux TCP 上把同一响应的两段交给 `writev`。连接复用两个切片描述符，发送结束或出错时清除值引用。空值只发头部。一次写截止时间覆盖完整响应，出站额度一直保留至发送返回。响应正文直接引用不可变值。 [Go `net.Buffers`](https://pkg.go.dev/net#Buffers.WriteTo)

用同一发压二进制和 250 µs 节拍，分别在 30k/s 回放小值、即时混合和慢读，在 100k/s 回放小值。每个负载跑三对，交换组内顺序。服务和客户端分别固定 CPU 0–1、2–5，服务容器上限 160 MiB。每轮新容器，连续发压 6 秒。服务端取 `/proc/1/stat` 用户态加内核态 CPU，并以 `/proc/1/io` 的 `syscw` 差值记录 `write` 和 `writev` 在内的进程写调用。用所有成功响应归一，其中小值组约 95% 是非空命中。在线 P99 从计划发送时刻计时，另报从实际发送到读完的 RTT P99，以及发压器 CPU、队列满和调度晚发。 [Linux 进程 I/O 计数](https://docs.kernel.org/filesystems/proc.html#proc-pid-io-display-the-io-accounting-fields) · [Linux `write` 和 `writev` 实现](https://github.com/torvalds/linux/blob/v6.14/fs/read_write.c)

采用向量写要求 30k/s 小值的每个成功响应服务 CPU 中位数至少下降 10%，并有至少两对观测到 RTT P99 同时下降 15% 和 0.03 ms，或同一高负载档至少两对的计划完成率增加 3 个百分点。常规负载还要保持协议、慢读资源边界和在线尾延迟。计划完成率以全部计划请求为分母。100k/s 逐段写的完成率已接近 98%，于是用同样条件补做三对 150k/s 小值回放，给高负载门槛留出可观测空间。

**实测。** 下表为三轮中位数，按逐段写 / 向量写排列。已发送请求均成功。慢读组每轮完成 240 个背景请求，两种路径采到的出站额度峰值均为 5–6 MiB。

| 负载 | 写调用 / 成功响应 | 服务 CPU ticks / 10 万个成功响应 | 在线 P99 ms | RTT P99 ms | 计划完成率 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 小值 30k/s | 1.952 / 1.002 | 34.4 / 30.0 | 4.01 / 4.13 | 1.05 / 1.38 | 99.98% / 99.95% |
| 混合 30k/s | 1.967 / 1.018 | 35.5 / 30.0 | 4.07 / 4.01 | 1.26 / 1.28 | 100% / 100% |
| 慢读 30k/s | 1.967 / 1.019 | 35.5 / 29.4 | 4.05 / 4.01 | 1.18 / 1.19 | 100% / 99.97% |
| 小值 100k/s | 1.951 / 1.000 | 28.3 / 22.6 | 4.02 / 3.92 | 0.97 / 0.99 | 97.72% / 97.90% |
| 小值 150k/s | 1.951 / 1.000 | 27.7 / 22.2 | 4.13 / 4.02 | 1.00 / 0.99 | 89.29% / 89.71% |

30k/s 小值组三对的服务 CPU 降幅为 8%–18%，中位数口径下降约 13%。三对 RTT P99 均上升。100k/s 小值的完成率配对变化为 +0.42、+0.14、−0.27 个百分点，150k/s 为 +0.36、+1.30、−0.54 个百分点。150k/s 的待发队列满计数中位数为 96,398 / 92,644，调度晚发每轮最多 675 个，客户端 CPU 中位数为 8.33 / 7.85 秒。队列计数定位了未发请求所在的位置，等待派发也受连接何时读完响应影响，单凭计数无法归因于发压器或服务上限。

**保留逐段写。** 向量写节省了约一次非空命中的写调用和一部分服务 CPU。在本机回环与这些负载下，客户端尾延迟和高负载完成率均未达到采用门槛。真实 TCP 测试覆盖空值，以及 1 MiB 响应在覆盖后完整读出旧值、写超时截断、客户端断开和出站额度归还。向量写只保留为复跑补丁。

## 一页对象的浅流水

一页读 16 个不同键，每个值 512 B，字节内容可区分。两组均用 16 条页读取连接和 16 条独立的单次 GET 连接，计划速率为每秒 1,250 页和 10,000 次单次 GET，合计每秒 30,000 次 GET。每个请求用同样的写入方式。窗口 1 写一帧、读一条；窗口 4 逐帧写完四个请求，再按序读完四条响应。每页完整校验键对应的值和顺序。实际在途以客户端已写完但尚未完整读到响应的请求数为准。

Linux arm64 回环，服务固定 CPU 0–1，发压器固定 CPU 2–5，服务容器上限 160 MiB。以 250 µs 节拍发压 6 秒，每组运行三轮，每对交换先后。验收要求两类计划完成率至少 99.5%，所有实际发送的请求完整且有序。窗口 4 应至少在两对中让整页发出至读完的 P50 降低 20%。若独立连接的计划至读完或 RTT P99 在至少两对中同时增加超过 0.2 ms 和 25%，继续定位干扰。

**实测。** 下表延迟为三轮中位数。页内每条延迟从开始写该帧计到对应正文验完，整页在线延迟还包含等待派发。

| 指标 | 逐条往返 | 窗口 4 |
| --- | ---: | ---: |
| 页连接 / 单次 GET 连接的在途峰值，每连接 | 1 / 1 | 4 / 1 |
| 每轮完成页数 / 计划 7,500 | 7,500 | 7,495–7,500 |
| 每轮完成旁路 GET / 计划 60,000 | 60,000 | 59,955–60,000 |
| 页内单条 GET P50 / P99 | 15.1 / 965 µs | 31.7 / 1,495 µs |
| 整页实际开始发送至读完 P50 / P99 | 0.309 / 5.81 ms | 0.172 / 3.67 ms |
| 整页计划发送至读完 P50 / P99 | 1.75 / 6.93 ms | 1.55 / 5.22 ms |

**保持服务端逐帧执行。** TCP 测试在同一串帧中验证了读己之写、`SET NX` 返回 `EXISTS` 后旧值仍在、出站 `BUSY` 后继续、二进制大值与小响应的顺序。大值堵住输出时，同连接后续写入要等它发送完；若发送超时截断，连接关闭，后续帧未执行。截断请求或入站 `BUSY` 同样终止连接，先前已确认的写仍然可读。客户端应限制在途请求数和预计回复字节数。实测覆盖回环小值和窗口 4，更大窗口、跨主机延迟与混合值需按各自负载验证。

## 闲置连接池的恢复

用真实 TCP 运行一条持续使用的连接和四条空闲连接，配置五个槽与 800 ms 读期限。满槽时并发发起四个连接并尝试 GET；旧连接关闭后再并发重连。热连接约每 40 ms 读取已确认的值。一条旧连接在期限过半时只发送部分 SET，观察它占用的 7 B 入站额度和原始读期限。验收要求热连接全部成功，四个槽在最后一个旧连接关闭后 400 ms 内重新可用，写入状态符合回包语义，在途额度归还到零。

| 三次 Linux TCP 回放 | 每轮观测 |
| --- | --- |
| 槽满时额外 GET | 0/4，均为 TCP 重置，无协议回包 |
| 旧连接结束 | 4/4 为 EOF，距上次完整响应约 800–804 ms |
| 部分 SET 的剩余等待 | 约 398–403 ms，关闭后入站额度归零 |
| 新连接读取原值 | 4/4，最后一次旧连接关闭后约 0.83–1.06 ms 完成，首批重连均成功 |
| 同一条热连接 | 22/22 GET 成功 |

本机另三轮也通过，满槽关闭表现为 EOF 或连接重置。部分 SET 和过期旧连接上重发的 SET 都未修改缓存。另一次 SET 刻意让写入者不读回包，第二条连接仍读到新值。客户端遇到无回包只能将结果视为未知。配套的 1 MiB 慢读用例实测了出站额度被占用，发送完成、超时或客户端断开后均归零。

默认配置用两条连接冒烟。一条每约 200 ms GET，75/75 读到已确认的值；另一条闲置约 15.4 s 后再发 SET，收到连接重置。新连接约 1.4 ms 内读到原值。该耗时来自本机回环。保持现有期限和资源上限，接入侧负责回收失效连接并控制重连并发。
