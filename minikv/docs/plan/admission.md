# 容量、淘汰与回填准入

外部应用负责回源。MiniKV 决定一个回填是否值得占用内存，以及写入失败时现有缓存会发生什么变化。多个客户端同时读取缺失键时，条件写只裁决谁成功填入缓存。若需要合并并发查询，由应用或 SDK 在回源前完成。

## 直接接纳的基线

每个分片同时限制槽位数和字节数。固定的索引与元数据从可用容量中预扣。覆盖已有条目只消耗净增加的条目字节，收取新值所占的临时空间另由入站额度承担。

在锁内形成有工作量上限的候选集合，排除目标键并去重。优先回收已过期条目，再按写入顺序从采样到的有效条目中选取。必须同时补足字节和槽位才能提交整个变更。某个分片可以先于全实例耗尽，返回其容量结果，指标分别报告分片使用量、采样成本和拒绝原因。

## 两次回填对照策略

在仅缺失回填需要挤出仍有效的值时，可在该分片用定期轮换的近似过滤器记录第一次尝试，返回“本次未缓存”。窗口内再次出现才走直接接纳路径。显式覆盖和仍有空间的插入沿用原规则。过滤器占用应从相同的总内存预算中扣除。次数门槛和轮换窗口都属于待测参数。

**验收。** 两组重放同一批请求，依次覆盖热点预热、一次性扫描和热点迁移。分别报告后端完成的查询数与 CPU 时间、业务成功率和 P99、缓存 P99.9、达到新热点稳定命中率的时间。复用[总设计中的判断门槛](design.md#缓存接近满载冷数据扫描后又发生热点迁移)，同时报告超时和拒绝，避免用降低成功率换取更少的后端工作。在代表性请求上观察到净收益后，再决定是否启用过滤器。

## 直接接纳基线预检

使用 Go 1.27.3 在 macOS arm64 回环连接上启动独立 MiniKV 进程。每轮新建单分片缓存，容量 585728 字节、512 槽，每次最多采样 16 槽。键为 8 字节，值为 1024 字节，TTL 为 10 分钟。单客户端依次发送请求，每次未命中执行一次 PBKDF2-SHA256（1500 轮）模拟回源 CPU 工作，随后用 `SET NX` 回填。

先填满 512 个键，再循环读取其中 128 个热点，共 4096 次。扫描期依次访问 1024 个只出现一次的冷键，每读一个冷键就轮读四次旧热点。扫描后改读 128 个新键，连读四遍。以下是三轮的中位数。在线延迟含缓存读取、模拟回源和回填，统计热点请求。后端 CPU 含全部未命中。

| 阶段 | 热点回源 | 冷键回源 | 后端 CPU | 在线 P99 | 热点缓存 GET P99.9 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 扫描前 | 0 / 4096 | 0 | 0 ms | 29.5 µs | 36.3 µs |
| 扫描期 | 317 / 4096 | 1024 | 485.6 ms | 479.4 µs | 72.9 µs |
| 新热点第一遍 | 128 / 128 | 0 | 46.5 ms | 515.9 µs | 71.5 µs |
| 新热点后续三遍 | 0 / 384 | 0 | 0 ms | 61.7 µs | 72.0 µs |

第一遍新热点耗时中位数为 61.3 ms，第二遍起全部命中。结果支持继续检验准入能否保住旧热点。服务采用直接接纳。启用准入需要在相同内存下完成对照，并验证代表性并发流量中的后端净收益和新热点预热门槛。这里的顺序回放和模拟回源用于复现污染现象，预热数据按遍数报告。

## 并发对照

服务运行在 Linux arm64 Docker 容器中，Go 1.27.3，限制为 2 CPU 和 64 MiB 内存，禁用额外交换空间，`GOMEMLIMIT=40MiB`。两组共用同一个服务二进制、TCP 协议、连接额度和 585728 字节缓存预算。缓存有一个分片、512 槽，每次写最多采样 16 槽。准入组预扣 8256 字节，用两个轮换位图记录当前和前一个 30 秒窗口内的回填尝试。

每组用相同的 504 个键预热。键为 8 字节，值为 1024 字节，TTL 为 10 分钟。16 个客户端连接每 20 毫秒各发一个计划请求。扫描期发送 5120 次请求，包含 1024 个一次性冷键和 4096 次旧热点读取。随后切换到 256 个新热点，连续读 40 秒。回源用并发上限为 8 的 PBKDF2-SHA256 模拟。每个未命中实际执行 1500 轮，逐请求累计线程 CPU 时间，之后以 `SET NX` 回填。

在线 P99 统计热点请求，从计划发出时刻计到读取、回源及回填结束。缓存 GET P99.9 统计同一批热点请求，仅计 TCP 读取往返。预热从切换起按连续的 10 秒窗口统计，连续三个窗口的命中率达到 95% 时完成。三对实验交替首跑顺序，每组启动新容器。

从 `minikv/` 复跑，使用本地 Linux 镜像，默认 `redis:7-alpine`。脚本从本地 Git 历史提取 `ff182ad95d5e664bc38a83cb3ecd8472947cb1d5` 的 MiniKV 到临时目录，并从该版本编译两组共用的实验服务。浅克隆需要先取到该提交。脚本以 JSON 行输出每组和每个阶段的原始数据。只验证 TCP 与响应差异时可跑短版。

```sh
python3 experiments/admission.py --pairs 3
python3 experiments/admission.py --pairs 1 --smoke
```

### 实测与决定

下表取三次运行的中位数。两阶段合计先按每轮求和，再取中位数。

| 指标 | 直接接纳 | 两次回填 | 变化 |
| --- | ---: | ---: | ---: |
| 扫描期旧热点回源 | 314 / 4096 | 2 / 4096 | −99.4% |
| 扫描期总回源 | 1338 | 1026 | −23.3% |
| 迁移期总回源 | 256 | 510 | +99.2% |
| 两阶段合计回源 | 1594 | 1537 | −3.6% |
| 两阶段合计后端 CPU | 1696.64 ms | 1443.18 ms | −14.9% |
| 扫描期在线 P99 | 10.24 ms | 8.42 ms | −17.7% |
| 扫描期热点 GET P99.9 | 11.16 ms | 11.21 ms | +0.4% |
| 迁移期在线 P99 | 8.76 ms | 9.75 ms | +11.3% |
| 迁移期热点 GET P99.9 | 11.68 ms | 13.23 ms | +13.2% |
| 新热点预热时间 | 30 s | 40 s | +33.3% |

每组每轮 37120 个请求全部成功，过载、容量拒绝和回源超时计数均为零。两次回填组的 `NOT_CACHED` 中位数在扫描期为 1024 次，在迁移期为 254 次。冷键首次访问仍需回源。保护旧热点节省的大部分查询被新热点多一次回填抵消。合计回源在三对实验中都下降，合计 CPU 在前两对分别增加约 2% 和 16%，第三对下降约 42%。

三对实验的预热时间一致。直接接纳首个窗口命中率为 96.8%，两次回填为 93.60%–93.64%，之后两组每个窗口均为 100%。第二对曾在 Docker 发布端口后、接受连接前启动回放。增加 TCP 就绪检查后重跑该对，表中采用完整配对。

**保留直接接纳。** 扫描期旧热点回源下降超过 30% 的目标，迁移期两项尾延迟分别超过 5% 的退化上限，预热增幅也超过 10%。常规服务只有直接接纳，历史对照继续使用原有两次回填实现。这组结果覆盖固定到达速率、单分片和模拟回源的并发回放。

### 实现边界验收

用同一组真实 TCP 请求对照移除前的 `8b14bf2` 和当前 CLI，配置单分片、3 槽、348 B 记账预算、3 个采样候选。两个版本的 19 个响应逐条一致。写满三个 3 B 值后，首次 `SET NX` 插入新键返回 `STORED`，淘汰最早写入的有效键。对现存键执行 `SET NX` 返回 `EXISTS`，原值保留。容量不足的覆盖返回 `NO_SPACE`，原值、原 TTL 和其他候选都保留。等原 TTL 到期后，`SET NX` 可以回填并读出新值。

历史短版每组完成扫描期 128 次与迁移期 8,000 次应用请求。一对回放中，直接接纳两期的 `NOT_CACHED` 均为零，两次回填组分别为 26 和 256。短版验证两组仍可复跑并产生各自的状态，性能取舍沿用上面的完整对照。
