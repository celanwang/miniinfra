# 容量、淘汰与回填准入

外部应用负责回源。MiniKV 决定一个回填是否值得占用内存，以及写入失败时现有缓存会发生什么变化。多个客户端同时读取缺失键时，条件写只裁决谁成功填入缓存。若需要合并并发查询，由应用或 SDK 在回源前完成。

## 直接接纳的基线

每个分片同时限制槽位数和字节数。固定的索引与元数据从可用容量中预扣。覆盖已有条目只消耗净增加的条目字节，收取新值所占的临时空间另由入站额度承担。

在锁内形成有工作量上限的候选集合，排除目标键并去重。优先回收已过期条目，再按写入顺序从采样到的有效条目中选取。必须同时补足字节和槽位才能提交整个变更。某个分片可以先于全实例耗尽，返回其容量结果，指标分别报告分片使用量、采样成本和拒绝原因。

## 值得实验的变化

在仅缺失回填需要挤出仍有效的值时，可在该分片用定期轮换的近似过滤器记录第一次尝试，返回“本次未缓存”。窗口内再次出现才走直接接纳路径。显式覆盖和仍有空间的插入沿用原规则。过滤器占用应从相同的总内存预算中扣除。次数门槛和轮换窗口都属于待测参数。

**验收。** 两组重放同一批请求，依次覆盖热点预热、一次性扫描和热点迁移。分别报告后端完成的查询数与 CPU 时间、业务成功率和 P99、缓存 P99.9、达到新热点稳定命中率的时间。复用[总设计中的判断门槛](design.md#缓存接近满载冷数据扫描后又发生热点迁移)，同时报告超时和拒绝，避免用降低成功率换取更少的后端工作。在代表性请求上观察到净收益后，再决定是否启用过滤器。

## 直接接纳基线预检

使用 Go 1.27.3 在 macOS arm64 回环连接上启动独立 MiniKV 进程。每轮新建单分片缓存，容量 585728 字节、512 槽，每次最多采样 16 槽。键为 8 字节，值为 1024 字节，TTL 为 10 分钟。单客户端依次发送请求，每次未命中执行一次 PBKDF2-SHA256（1500 轮）模拟回源 CPU 工作，随后用 `SET NX` 回填。

先填满 512 个键，再循环读取其中 128 个热点，共 4096 次。扫描期依次访问 1024 个只出现一次的冷键，每读一个冷键就轮读四次旧热点。扫描后改读 128 个新键，连读四遍。以下是三轮的中位数。在线延迟含缓存读取、模拟回源和回填，统计热点请求。后端 CPU 含全部未命中。

| 阶段 | 热点回源 | 冷键回源 | 后端 CPU | 在线 P99 | 热点缓存 GET P99.9 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 扫描前 | 0 / 4096 | 0 | 0 ms | 29.5 µs | 36.3 µs |
| 扫描期 | 317 / 4096 | 1024 | 485.6 ms | 479.4 µs | 72.9 µs |
| 新热点第一遍 | 128 / 128 | 0 | 46.5 ms | 515.9 µs | 71.5 µs |
| 新热点后续三遍 | 0 / 384 | 0 | 0 ms | 61.7 µs | 72.0 µs |

第一遍新热点耗时中位数为 61.3 ms，第二遍起全部命中。结果支持继续检验准入能否保住旧热点。服务采用直接接纳。启用准入需要在相同内存下完成对照，并验证代表性并发流量中的后端净收益和新热点预热门槛。这里的顺序回放和模拟回源用于复现污染现象，预热数据按遍数报告。
