# 近满写入、接收缓冲与部署内存

用于核对大值写入、接收池和 Go 内存设置怎样影响进程峰值与前台延迟。当前实现见[大值接收缓冲](../plan/connections.md#大值接收缓冲)，共享环境和命令入口见[容量与性能回放](../plan/capacity.md#负载与复现)。

## 近满写入与进程内存

| 服务和运行配置 | 1 KiB 预填 | 256 次 1 MiB 写入 | 进程 RSS |
| --- | --- | --- | --- |
| MiniKV，默认 Go 内存设置 | 两次定位复跑均完成 100000 次 | 三轮被 cgroup OOM 终止。两次定位复跑均在预填完成后终止 | 以 160 MiB cgroup 硬限制的 OOM 事件判定 |
| MiniKV，`GOMEMLIMIT=112MiB` | 两轮均完成 100000 次 | 两轮均返回 256 次 `NO_SPACE`，`BUSY` 和超时为 0 | 两轮结束为 107.0、109.0 MiB，峰值为 128.6、113.2 MiB |
| Redis，64 MiB `maxmemory` | 全部成功 | 每轮均接受 256 次写入 | 峰值 124.9–126.7 MiB |

MiniKV 的两个软限制对照里，每个分片预填后均有 3612 条，记账 4193560 字节，剩余 744 字节。16 个采样候选最多腾出 16544 字节，无法满足一笔 1 MiB 插入。因此这批 `NO_SPACE` 是有界淘汰的结果，两轮合计回收增量都为 0。Redis 能从整个实例淘汰大量小值来接纳大写，写入成功反映了不同的淘汰契约。

| 分片 | 第一次软限制对照的 `NO_SPACE` | 第二次软限制对照的 `NO_SPACE` |
| --- | --- | --- |
| 0–7，依次 | 21, 19, 9, 11, 18, 18, 17, 12 | 16, 16, 16, 23, 11, 15, 13, 17 |
| 8–15，依次 | 19, 13, 11, 15, 20, 16, 17, 20 | 20, 18, 19, 10, 18, 16, 14, 14 |

MiniKV 先按网络额度收齐写入体，再裁决分片容量。即使写入后续被拒，准备这些值仍产生短期分配。64 MiB 缓存额度约束条目，部署还需要给运行时、内核与在途数据留出余量。对于这里的 160 MiB 容器，112 MiB 软限制在两轮中让实例存活并返回其完整的容量结果。这个设置是本实验的对照值，软限制的延迟和 CPU 代价尚需随部署负载验证。 [Go GC 内存限制](https://go.dev/doc/gc-guide#Memory_limit)

```sh
python3 experiments/capacity.py --profiles capacity
python3 experiments/capacity.py --profiles capacity --go-memory-limit 112MiB
```

## 近满写入并发小读

沿用 64 MiB 缓存、160 MiB cgroup 上限、100000 个 1 KiB 预填、8 条连接提交 256 次 1 MiB 写入。预填后放入 16 个 512 B 热键，16 条小读连接按 10k/s 计划速率回放 2 秒。大值写在小读开始约 250 ms 后发起。P99 按请求的计划时点分为写入前、写入期间和写入后，仅统计完整命中，未发和失败另计。每条写连接的最后一次请求结束后，在同一连接读一个热键以校验协议恢复。

Go 1.27.3，Linux arm64 Docker，服务固定在 CPU 0–1，驱动固定在 CPU 2–5，各自仍受 2 和 4 CPU 配额限制。旧实现取自 `03d0905`。默认 Go 设置下旧实现与缓冲复用版本交替先后顺序，共三对，每次用新容器，串行运行。旧实现的 112 MiB 软限制对照独立跑三轮，采用相同固定 CPU 与协议负载。启动时同一 Docker 引擎没有其他运行容器。宿主调度仍共享，这里的尾延迟只用于比较本次负载。cgroup 和运行时计数从隔离容器内采样，RSS 来自 Linux 进程状态，失败组的峰值取退出前能采到的值，OOM 由 Docker 状态确认。累计分配、GC 与 CPU 的差值使用写入前后快照。

| --- | ---: | ---: | ---: |
| OOM | 3/3 | 0/3 | 0/3 |
| 大值写返回 `NO_SPACE` | 56–101 / 256 | 256 / 256 | 256 / 256 |
| 写连接可在原连接继续读 | 0 / 8 | 8 / 8 | 8 / 8 |
| 写入后小读成功数 | 0 | 14345–14618 | 15378–15693 |

| 写入窗口分配 | 58.39–93.41 MiB，退出前采样 | 256.95–257.03 MiB | 8.39–8.57 MiB |
| cgroup 内存峰值 | 154.75–160.00 MiB，退出前采样 | 118.60–127.83 MiB | 115.89–128.54 MiB |

软限制对照和缓冲复用版本每轮完成全部 20000 次小读，`BUSY`、超时和连接错误为 0。缓冲复用版本每轮写入期间有 1792–2100 个小值命中，软限制对照有 2877–3150 个。旧实现的 155–200 个大写连接错误出现在实例退出期间，成功小读的延迟样本只代表退出前的一部分请求。

在途入站峰值约 8 MiB，旧实现仍会为每次被拒的请求分配一个临时值。这里主要耗尽的是重复分配与垃圾回收之间的堆余量。软限制通过更频繁的回收让实例存活。复用精确长度的未发布缓冲使写入窗口的中位分配下降约 97%，保留了原容量结果和帧边界。代价是默认最多持有 8 MiB 空闲缓冲。写入期间的小读 P99 中位数为 11.92 ms，软限制对照为 11.88 ms。这两组的峰值 RSS 区间重叠。本轮保留显式配置运行时软限制的部署能力，并使用有界复用降低本场景的分配压力。

在各版本的组件目录运行。两组命令分别从 `03d0905` 和含缓冲复用的版本构建服务与驱动。依次运行，避免同一宿主的两个实验竞争。

```sh
python3 experiments/capacity.py --profiles pressure --server-cpus 0-1 --driver-cpus 2-5
python3 experiments/capacity.py --profiles pressure --server-cpus 0-1 --driver-cpus 2-5 --go-memory-limit 112MiB
```

### 按接收容量复用

64 KiB 及以上的大值按 4 KiB 取整接收，申请实际接收容量的在途额度。额度或单值上限不足时回退至精确长度。只有通过分片裁决的写入才会发布。精确容量的缓冲可直接交给条目，取整缓冲在写锁内复制出精确容量的值，原缓冲继续受空闲池上限约束。被拒写入既不用复制，也不会改变现有条目。

以 `52114c0` 的精确长度版本为对照。同一驱动，在固定 CPU、160 MiB 硬上限和默认 Go 内存设置下，各做三对交替顺序的回放。取整版本每一轮都返回 256 个 `NO_SPACE`，完成 20000 次小读，且 8 条写连接都能继续读。表中分配统计写入前后的累计分配差，中位数和 P99 只取完整轮。

| 长度 | 精确长度 OOM | 取整 OOM | 两组分配中位数 MiB | 两组写入期间小读 P99 中位数 | 取整版 cgroup 峰值 MiB |
| --- | ---: | ---: | ---: | ---: | ---: |
| 固定 1 MiB | 0/3 | 0/3 | 8.40 / 8.50 | 10.06 / 10.42 ms | 118.0–128.1 |
| 四种轮换 | 1/3 | 0/3 | 33.06 / 22.41 | 11.52 / 11.03 ms | 127.2–139.0 |
| 256 种相邻 | 3/3 | 0/3 | — / 8.42 | — / 12.09 ms | 109.6–121.5 |

取整版空闲缓冲在这些轮次的采样峰值为 7–8 MiB，发布值记账和连接额度各自独立。固定长度的分配近似持平。轮换组完整样本的分配下降，相邻互异组回到与固定组相近的分配量。软限制仍是部署上可单独评估的配置。这些结果覆盖指定长度与并发组合，尺寸跨度更大或发布成功比例更高时，堆和锁竞争的边界仍需实测。

### 成功大写的代价

`publish` 模式保留 16 条小读连接，用 8 条写连接固定覆盖两个缓存键，共成功写入 256 次。每个值为 1 MiB 少 1 字节，每次走取整缓冲后精确复制的路径。缓存工作集有余量，用于单独观察发布成本。在相同设置下另做三对逐写延迟回放，每轮有 256 个写延迟样本。写 P99 从开始发送到完整收到响应，小读 P99 沿用计划时点口径。精确长度的一轮出现 2 次发压器晚发，两组所有发出的小读均成功。

| 指标，中位数 | 精确长度 | 取整接收 |
| --- | ---: | ---: |
| 写入窗口累计分配 | 256.77 MiB | 263.68 MiB |
| 成功 SET P99 | 8.94 ms | 11.26 ms |
| 写入期间小读 P99 | 11.69 ms | 10.57 ms |
| 写入窗口 cgroup CPU | 57.29 ms | 57.79 ms |
| cgroup 峰值 | 43.39 MiB | 51.65 MiB |
| 进程 RSS 峰值 | 43.73 MiB | 50.77 MiB |
| 空闲缓冲峰值 | 0 MiB | 8 MiB |

精确长度组三轮写 P99 为 8.63–11.46 ms，取整组为 9.44–12.57 ms。成功取整写需要一次锁内复制，也可能同时持有接收与发布两份缓冲。本次接受这一成本，以获取近满拒绝场景的内存收益。下一项待验证的问题是，在保持原子发布和精确字节记账的条件下，能否减少成功大写的锁内复制时间。

在当前组件目录依次运行以下命令，沿用上一节解出的精确长度源码。对照可以交替运行顺序。


### 同分片覆盖对照

本轮将 256 次大写集中到一个现存键。16 条小读连接平均分组，各读 8 个已预热的 512 B 键。一组使用写入所在分片，另一组使用相邻分片，两组分别收到同一计划速率的半数请求。测试入口提供实际分片映射，发压器按映射选键。服务与驱动仍各自固定在 CPU 0–1 与 2–5，使用相同的 160 MiB 硬上限、2 秒小读计划及默认 Go 内存设置。每轮使用新容器，串行、交替顺序运行。正式对照每轮开始前均无其他运行中的 Docker 容器，宿主调度仍可能引入波动。

先比较现有服务的 `publish-locality`（1 MiB 少 1 字节，锁内复制）与 `publish-aligned`（1 MiB，接收缓冲直接移交）。三对普通回放中，写 P99 中位数为 11.58 和 13.82 ms，同分片小读 P99 中位数为 13.70 和 14.54 ms，跨分片为 13.41 和 14.46 ms。对齐的一轮有 5 个调度晚发。普通端到端数据未复现先前双写键实验的写 P99 排序。

带阻塞采样的独立轮次记录到局部成本。两次未对齐验收分别采到 79 和 103 次 `Store.Get` 的读锁阻塞，累计阻塞约 20.5 和 20.6 ms。对齐控制未采到该调用栈。这个对照通常同时移除了锁内分配和复制，采样能定位等待发生的位置，尚无法拆出分配、复制和调度各自的耗时。阻塞采样轮次用于归因，下面的 TCP 延迟来自关闭采样的回放。

**候选方案。** 在读取值体前，对非 NX 等容量覆盖做一次读锁检查。命中时使用精确接收缓冲，按实际容量调整入站额度，读完值体后照常在写锁内检查当前状态并发布。这样能移除这一类覆盖的锁内复制，已有条目或容量的后续变化仍由原有路径裁决。未通过裁决的完整帧仍返回对应响应，缓冲归还遵守原额度。

| 指标，五对普通回放的中位数 | 现有锁内复制 | 直接精确接收候选 |
| --- | ---: | ---: |
| 成功 SET P99 | 12.32 ms | 14.69 ms |
| 同分片小读 P99 | 13.96 ms | 14.04 ms |
| 跨分片小读 P99 | 12.87 ms | 14.08 ms |
| 同分片小读 RTT P99 | 10.27 ms | 10.51 ms |
| 跨分片小读 RTT P99 | 10.01 ms | 10.63 ms |
| 写窗口累计分配 | 263.94 MiB | 256.77 MiB |
| 写窗口 cgroup CPU | 58.75 ms | 56.27 ms |
| cgroup 峰值 | 45.71 MiB | 37.31 MiB |
| 进程 RSS 峰值 | 50.72 MiB | 42.99 MiB |
| 空闲接收缓冲峰值 | 8 MiB | 1 MiB |

每轮均成功完成 256 次覆盖，8 条写连接随后都能读取。每轮计划 20000 次小读，全部已发小读成功。候选的一轮有 7 次调度晚发，其余轮均完整发出。写入期间每组每轮有 930–1570 个小读样本。现有路径与候选的 SET P99 区间分别为 9.30–16.74 ms 和 12.13–19.08 ms，候选在五对中有四对更高。同分片小读无稳定收益，两组小读的高点常同时出现在同一轮。

另做两对带阻塞采样的比较，现有服务分别记录 63 和 77 次 `Store.Get` 读锁阻塞，累计 16.6 和 124.1 ms。候选两轮均未采到该栈。固定、轮换和相邻互异的近满拒写回归各做两对，两侧均为每轮 256 个 `NO_SPACE`、20000 次小读完成、8 条连接可继续读，且 OOM 为 0。候选的专项竞态测试验证了旧响应不可变、读取值体期间容量变化后重新裁决，以及拒绝后原连接仍能读取。仓库的条件写入口为 `SET NX`。

**保留现有实现。** 候选减少了采样中的读锁等待和这一成功覆盖场景的峰值内存，端到端小读收益欠稳定，写 P99 也偏高。保留实验补丁，以便用相同驱动验证这项取舍。下一步优先用执行跟踪分开计量网络收发、goroutine 唤醒和发布等待，解释同分片与跨分片尾延迟为什么同时变化。

从最终版本的组件目录运行，同一驱动分别构建现有 peer 和临时目录中的候选 peer。正式测时去掉 `--block-profile`，归因时单独开启。也可把 `--pressure-lengths` 改为 `fixed`、`repeated` 或 `adjacent` 复跑近满回归。

```sh

patch_file="$PWD/experiments/equal-overwrite.patch"
git -C .. archive b403cd0 minikv | tar -xf - -C "$peer_source"
(cd "$peer_source" && git apply --unidiff-zero "$patch_file")
GOWORK=off python3 experiments/capacity.py --profiles pressure --pressure-lengths publish-aligned \
    --server-cpus 0-1 --driver-cpus 2-5
GOWORK=off python3 experiments/capacity.py --profiles pressure --pressure-lengths publish-locality \
    --server-cpus 0-1 --driver-cpus 2-5
GOWORK=off python3 experiments/capacity.py --profiles pressure --pressure-lengths publish-locality \
    --server-cpus 0-1 --driver-cpus 2-5 --peer-module "$peer_source/minikv"
```

### 空闲池跨尺寸切换

空闲池的旧策略在仍有空间时才接受归还。白盒测试把 8 MiB 填满于单个尺寸，再归还另一尺寸，两个方向都会丢掉新缓冲。后续该尺寸即使反复出现，也不会获得可复用的槽位。

沿用默认 16 分片、64 MiB 缓存、160 MiB cgroup 硬上限和默认 Go 内存设置。预填 100000 个 1 KiB 小值，再由 16 条连接按 10k/s 计划速率发出 20000 次小读。第一阶段使用正常 TCP SET，将每条值体保留最后一字节，等所有请求取得入站额度再发送最后一字节。1 MiB 用 8 条连接，512 KiB 用 16 条。两组保持同一进程，结束时确认空闲池确实占满 8 MiB。随后用 8 条连接发出 256 MiB 的另一尺寸写入。冷启动对照从相同的新进程预填后跳过第一阶段。

两组用同一驱动，以 Go 1.27.3 在 Linux arm64 Docker 中串行交替。服务器固定 CPU 0–1，驱动固定 CPU 2–5。每轮启动前等待其他 Docker 容器退出，宿主调度仍共享。分配量取阶段前后累计分配差，OOM 时取最后可采样值。cgroup 峰值取阶段内采到的累计高水位，可能包含预填或上一阶段。小读 P99 从计划时刻计到完整命中，失败和未发另计。

| 第一阶段，六轮范围 | `NO_SPACE` | 原连接继续读 | 阶段分配 | cgroup 高水位 | 阶段小读成功 / P99 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 用 1 MiB 填池 | 8 / 8 | 8 / 8 | 8.02–8.16 MiB | 101.7–128.8 MiB | 225–562 / 5.51–13.72 ms |
| 用 512 KiB 填池 | 16 / 16 | 16 / 16 | 8.05–8.18 MiB | 109.3–127.5 MiB | 315–560 / 6.33–13.31 ms |

| 第二阶段，三对各方向 | OOM | `NO_SPACE` | 整轮小读成功 | 原写连接继续读 | 阶段分配 | cgroup 高水位 | 小读 P99 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 MiB → 512 KiB，旧策略 | 3/3 | 85–180 / 512 | 3555–4107 | 0 / 8 | 43.58–86.28 MiB | 160.0 MiB | 13.73–40.08 ms，部分完成 |
| 1 MiB → 512 KiB，替换最早归还 | 0/3 | 512 / 512 | 20000 | 8 / 8 | 4.51–4.64 MiB | 106.5–133.1 MiB | 11.46–12.80 ms |
| 512 KiB → 1 MiB，旧策略 | 3/3 | 36–53 / 256 | 3275–3471 | 0 / 8 | 34.02–54.20 MiB | 157.3–160.0 MiB | 13.65–55.25 ms，部分完成 |
| 512 KiB → 1 MiB，替换最早归还 | 0/3 | 256 / 256 | 20000 | 8 / 8 | 8.31–8.50 MiB | 117.5–129.5 MiB | 8.96–12.85 ms |

替换策略在两方向的进程 RSS 峰值分别为 112.6–130.3 和 123.2–134.6 MiB，空闲缓冲上限仍为 8 MiB。旧策略六轮都在第二阶段退出，退出后小读无成功结果。两轮冷启动里，两种策略都能完整拒绝大写，512 KiB 分配为 4.49–4.65 MiB，1 MiB 为 8.24–8.33 MiB。切换后的分配回到冷启动量级。

另做三对交替回放，每批 8 个写在 1 MiB 和 512 KiB 间切换，总共 384 个写。两组每轮均完整拒写且无 OOM。旧策略分配 38.03–39.91 MiB，替换策略为 22.86–35.50 MiB。小读 P99 从 10.39–11.20 ms 变为 10.96–12.07 ms。单对四尺寸轮换的分配从 23.04 增至 26.46 MiB，单对相邻互异的分配近似持平。两对成功覆盖均完成 256 个 SET，阶段分配维持在 263.48–263.61 MiB。控制组部分轮次有少量驱动晚发，所有已发小读和同连接恢复检查均成功。

采用按归还顺序替换。症状来自一个尺寸的空闲缓冲长期占满预算，替换只在归还空间不足时发生。池仍按实际 backing 容量记账，容量上限不变。交替对照显示分配下降，但小读尾延迟没有一致改善，更宽的尺寸分布仍需实测。

```sh
    GOWORK=off python3 experiments/capacity.py --profiles pressure --pressure-lengths "$lengths" \
```

### 宽尺寸混合回放

这轮用一个合成业务回放验收尺寸替换后的部署边界。沿用 16 分片、64 MiB 缓存、160 MiB cgroup 上限、2 CPU 服务和 4 CPU 驱动。服务器固定 CPU 0–1，驱动固定 CPU 2–5。使用 Linux arm64 Docker 和 Go 1.27.3。每轮启动前等待其他 Docker 容器结束，每对交换先跑顺序，宿主调度仍共享。

预填 100000 个 1 KiB 值时保留一个分片给覆盖写。其他分片逼近容量上限，正式写入前的缓存记账为 62.62 MiB。16 条小读连接在 2 秒内计划发送 20000 次热点 512 B GET。8 条写连接提交 512 次 SET，每四次写约有一次覆盖已有键，其余尝试向近满分片插入。覆盖使用 512 B 至接近 1 MiB 的 15 种长度，共约 35.02 MiB 值体。插入使用 64 KiB 至 1 MiB 的 10 种长度，共约 160.25 MiB，后半段中大值更密集。键按各实例的实际分片路由选择。驱动逐笔检查 `STORED` 与 `NO_SPACE`，结束时通过原连接逐字节核验 8 个最新值。

验收要求三轮均存活，每轮 128 个 `STORED`、384 个 `NO_SPACE`，8 条写连接可继续读取且最终值校验通过。已发小读全部成功，计划完成率至少 99.5%。同时记录分配、堆、进程 RSS、容器峰值和尾延迟。冒烟中默认 Go 设置触发 OOM，因此正式对照选择同一实现的 `GOMEMLIMIT=112MiB`，只改变这个运行时参数。冒烟轮独立记录，以下是三对正式回放。

默认设置的两个失败轮在退出前分别返回 107 / 324 和 105 / 319 个 `STORED` / `NO_SPACE`，其余 81 和 88 个写出现连接错误，两轮完成 3694 和 3566 次小读。失败轮最后采到的 cgroup 高水位为 153.67–159.28 MiB，OOM 由容器状态确认。默认设置的成功轮在写前占用 102.96 MiB，两次失败轮均约为 115 MiB。软限制组的空闲缓冲采样峰值为 7.63–7.95 MiB，池的 8 MiB 上限保持有效。写 P99 包含两类完整 SET 响应，只有一个完整默认轮可供对照，尾延迟数据用于描述代价。

**收束接收池优化。** 这组负载在默认 Go 设置下会耗尽 160 MiB 的部署余量，软限制对照三轮达到验收门槛。完整轮分配量在两种设置下重叠，软限制减少了峰值并增加了 GC 工作。证据支持把这个边界作为部署约束，保留当前缓冲替换和发布逻辑。112 MiB 是这个容器和负载下的实测值，其他内存配置、持续时长及分布仍需按部署验证。
