# TCP 连接与响应实验

用于核对[当前小值合并发送](#小值合并发送)、客户端[浅流水](#一页对象的浅流水)和[重连](#闲置连接池的恢复)，并保留先前的发送与分配对照。现行连接契约见[连接与在途额度](../plan/connections.md)。命令从组件目录运行，默认负载和公共配置见[容量与性能回放](../plan/capacity.md)。

## 小 GET 响应发送

逐段写基线先发 `VALUE` 头，再发非空值。对照用 `net.Buffers.WriteTo`，在 Linux TCP 上把同一响应的两段交给 `writev`。连接复用两个切片描述符，发送结束或出错时清除值引用。空值只发头部。一次写截止时间覆盖完整响应，出站额度一直保留至发送返回。响应正文直接引用不可变值。 [Go `net.Buffers`](https://pkg.go.dev/net#Buffers.WriteTo)

用同一发压二进制和 250 µs 节拍，分别在 30k/s 回放小值、即时混合和慢读，在 100k/s 回放小值。每个负载跑三对，交换组内顺序。服务和客户端分别固定 CPU 0–1、2–5，服务容器上限 160 MiB。每轮新容器，连续发压 6 秒。服务端取 `/proc/1/stat` 用户态加内核态 CPU，并以 `/proc/1/io` 的 `syscw` 差值记录 `write` 和 `writev` 在内的进程写调用。用所有成功响应归一，其中小值组约 95% 是非空命中。在线 P99 从计划发送时刻计时，另报从实际发送到读完的 RTT P99，以及发压器 CPU、队列满和调度晚发。 [Linux 进程 I/O 计数](https://docs.kernel.org/filesystems/proc.html#proc-pid-io-display-the-io-accounting-fields) · [Linux `write` 和 `writev` 实现](https://github.com/torvalds/linux/blob/v6.14/fs/read_write.c)

采用向量写要求 30k/s 小值的每个成功响应服务 CPU 中位数至少下降 10%，并有至少两对观测到 RTT P99 同时下降 15% 和 0.03 ms，或同一高负载档至少两对的计划完成率增加 3 个百分点。常规负载还要保持协议、慢读资源边界和在线尾延迟。计划完成率以全部计划请求为分母。100k/s 逐段写的完成率已接近 98%，于是用同样条件补做三对 150k/s 小值回放，给高负载门槛留出可观测空间。

**实测。** 下表为三轮中位数，按逐段写 / 向量写排列。已发送请求均成功。慢读组每轮完成 240 个背景请求，两种路径采到的出站额度峰值均为 5–6 MiB。

| 负载 | 写调用 / 成功响应 | 服务 CPU ticks / 10 万个成功响应 | 在线 P99 ms | RTT P99 ms | 计划完成率 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 小值 30k/s | 1.952 / 1.002 | 34.4 / 30.0 | 4.01 / 4.13 | 1.05 / 1.38 | 99.98% / 99.95% |
| 混合 30k/s | 1.967 / 1.018 | 35.5 / 30.0 | 4.07 / 4.01 | 1.26 / 1.28 | 100% / 100% |
| 慢读 30k/s | 1.967 / 1.019 | 35.5 / 29.4 | 4.05 / 4.01 | 1.18 / 1.19 | 100% / 99.97% |
| 小值 100k/s | 1.951 / 1.000 | 28.3 / 22.6 | 4.02 / 3.92 | 0.97 / 0.99 | 97.72% / 97.90% |
| 小值 150k/s | 1.951 / 1.000 | 27.7 / 22.2 | 4.13 / 4.02 | 1.00 / 0.99 | 89.29% / 89.71% |

30k/s 小值组三对的服务 CPU 降幅为 8%–18%，中位数口径下降约 13%。三对 RTT P99 均上升。100k/s 小值的完成率配对变化为 +0.42、+0.14、−0.27 个百分点，150k/s 为 +0.36、+1.30、−0.54 个百分点。150k/s 的待发队列满计数中位数为 96,398 / 92,644，调度晚发每轮最多 675 个，客户端 CPU 中位数为 8.33 / 7.85 秒。队列计数定位了未发请求所在的位置，等待派发也受连接何时读完响应影响，单凭计数无法归因于发压器或服务上限。

**本轮保留逐段写。** 向量写节省了约一次非空命中的写调用和一部分服务 CPU。在本机回环与这些负载下，客户端尾延迟和高负载完成率均未达到采用门槛。真实 TCP 测试覆盖空值，以及 1 MiB 响应在覆盖后完整读出旧值、写超时截断、客户端断开和出站额度归还。向量写只保留为复跑补丁。

从组件目录准备两个对照服务，复用当前驱动。只取输出中 `Engine` 为 `minikv` 的行，每对交换 `direct` 与 `vector` 的顺序。用同样参数把负载改成 `--profiles small --rates 100000,150000`，可复跑高负载。

### 小值合并发送

在 `ef54ed2` 上，以 100k/s 重放小值，采两次 32 秒 Go CPU profile。Linux arm64、Go 1.27.3，服务与驱动分别使用 CPU 10–11 和 12–15，资源限制沿用集成版复跑。两次各完成约 316 万个请求。剖析采到 10.29 和 10.02 秒 CPU，同窗口 `/proc/1/stat` 为 10.44 和 10.16 秒，其中系统态约占三分之二。两轮无剖析对照的完成率约为 99%，写调用约为 1.95 次/完成响应。

按调用栈互斥计数，TCP 写栈占 59%–61%，读栈占 18%–20%，连接读写栈以外的 Go 调度与轮询约占 6%。存储栈含读时的出站预留，占约 5%–6%。截止时间设置约占 4%，头部解析约占 1%，其余主要在连接处理。Go 栈能定位写系统调用的入口，内核 TCP 子路径的成本仍需内核剖析。

非空且不超过 512 B 的值复制到连接的回复缓冲，与头部一起发送。缓冲首次用到时从 32 B 扩到 544 B，随后复用。更大的值继续逐段发送，直接引用缓存值。写期限覆盖完整响应，出站额度在写完或中止时归还。

无剖析的小值和慢读各做四对，交替首跑顺序，各有两次逐段写复跑。仍以 100k/s 和 250 µs 节拍运行，小值每轮 8 秒，慢读每轮 6 秒。下表为合并发送相对逐段写的配对中位变化，CPU 以全部成功完成响应归一，延迟统计普通组 GET。

| 场景 | CPU/响应 | 系统态 CPU/响应 | 完成率 | 在线 P99 | RTT P99 / P99.9 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 小值 | −21.1% | −27.9% | +0.11 个百分点 | −3.3% | +0.7% / +2.4% |
| 慢读 | −23.6% | −29.6% | +0.23 个百分点 | −5.2% | −2.4% / −5.1% |

八对的总 CPU 均下降，同版本复跑的 CPU/响应差异为 2%–14%。写调用约从 1.95 降至 1.00 次/响应，RTT 在配对间有升有降。已发送请求全成功，慢读出站峰值为 5–6 MiB，结束时为零。TCP 回归逐字节检查 0、512 和 513 B 回复，以及 1 MiB 慢读时的旧值、超时、断开和额度回收。采用依据是可重复的 CPU 收益，适用范围为本次 Linux 回环负载。

复跑时在组件目录用现有发压器，交错当前服务和基线，只取 `Engine` 为 `minikv` 的行。采集 CPU profile 时可在临时基线的诊断 mux 注册 `pprof.Profile`，预填和建连后请求 `/debug/pprof/profile?seconds=32`，用 `go tool pprof -top -cum` 查看，再以同窗口 `/proc/1/stat` 的第 14、15 字段与 `/proc/1/io` 的 `syscw` 差值核对。

```sh
old=$(mktemp -d)
git -C .. archive ef54ed2 minikv | tar -xf - -C "$old"
for module in "$old/minikv" "$PWD"; do
    GOWORK=off python3 experiments/capacity.py --profiles small --rates 100000 --duration 8s \
        --tick 250us --server-cpus 10-11 --driver-cpus 12-15 --peer-module "$module"
    GOWORK=off python3 experiments/capacity.py --profiles slow --rates 100000 --duration 6s \
        --tick 250us --server-cpus 10-11 --driver-cpus 12-15 --peer-module "$module"
done
```

## 一页对象的浅流水

一页读 16 个不同键，每个值 512 B，字节内容可区分。两组均用 16 条页读取连接和 16 条独立的单次 GET 连接，计划速率为每秒 1,250 页和 10,000 次单次 GET，合计每秒 30,000 次 GET。每个请求用同样的写入方式。窗口 1 写一帧、读一条；窗口 4 逐帧写完四个请求，再按序读完四条响应。每页完整校验键对应的值和顺序。实际在途以客户端已写完但尚未完整读到响应的请求数为准。

Linux arm64 回环，服务固定 CPU 0–1，发压器固定 CPU 2–5，服务容器上限 160 MiB。以 250 µs 节拍发压 6 秒，每组运行三轮，每对交换先后。验收要求两类计划完成率至少 99.5%，所有实际发送的请求完整且有序。窗口 4 应至少在两对中让整页发出至读完的 P50 降低 20%。若独立连接的计划至读完或 RTT P99 在至少两对中同时增加超过 0.2 ms 和 25%，继续定位干扰。

**实测。** 下表延迟为三轮中位数。页内每条延迟从开始写该帧计到对应正文验完，整页在线延迟还包含等待派发。

| 指标 | 逐条往返 | 窗口 4 |
| --- | ---: | ---: |
| 页连接 / 单次 GET 连接的在途峰值，每连接 | 1 / 1 | 4 / 1 |
| 每轮完成页数 / 计划 7,500 | 7,500 | 7,495–7,500 |
| 每轮完成旁路 GET / 计划 60,000 | 60,000 | 59,955–60,000 |
| 页内单条 GET P50 / P99 | 15.1 / 965 µs | 31.7 / 1,495 µs |
| 整页实际开始发送至读完 P50 / P99 | 0.309 / 5.81 ms | 0.172 / 3.67 ms |
| 整页计划发送至读完 P50 / P99 | 1.75 / 6.93 ms | 1.55 / 5.22 ms |
| 旁路单次 GET 计划发送至读完 P99 | 4.07 ms | 4.20 ms |
| 旁路单次 GET RTT P99 | 2.17 ms | 1.98 ms |

六轮都完成了已发请求。仅窗口 4 的一轮有 5 页和 45 次旁路 GET 因调度晚发而未发。整页发送至读完的 P50 在三对中下降 39%–46%。旁路计划至读完 P99 增加 0.10–0.41 ms，实际 RTT P99 下降 0.03–0.53 ms。三对达到验收条件。对需要齐整页的应用，窗口 4 可以减少等待轮数，单条 GET 则可能多等同批其他请求发出或前序响应读完。

**保持服务端逐帧执行。** TCP 测试在同一串帧中验证了读己之写、`SET NX` 返回 `EXISTS` 后旧值仍在、出站 `BUSY` 后继续、二进制大值与小响应的顺序。大值堵住输出时，同连接后续写入要等它发送完；若发送超时截断，连接关闭，后续帧未执行。截断请求或入站 `BUSY` 同样终止连接，先前已确认的写仍然可读。客户端应限制在途请求数和预计回复字节数。实测覆盖回环小值和窗口 4，更大窗口、跨主机延迟与混合值需按各自负载验证。

```sh
for depth in 1 4; do
    GOWORK=off python3 experiments/capacity.py --profiles page --rates 1250 \
        --page-window "$depth" --tick 250us --server-cpus 0-1 --driver-cpus 2-5
done
```

## 闲置连接池的恢复

用真实 TCP 运行一条持续使用的连接和四条空闲连接，配置五个槽与 800 ms 读期限。满槽时并发发起四个连接并尝试 GET；旧连接关闭后再并发重连。热连接约每 40 ms 读取已确认的值。一条旧连接在期限过半时只发送部分 SET，观察它占用的 7 B 入站额度和原始读期限。验收要求热连接全部成功，四个槽在最后一个旧连接关闭后 400 ms 内重新可用，写入状态符合回包语义，在途额度归还到零。

| 三次 Linux TCP 回放 | 每轮观测 |
| --- | --- |
| 槽满时额外 GET | 0/4，均为 TCP 重置，无协议回包 |
| 旧连接结束 | 4/4 为 EOF，距上次完整响应约 800–804 ms |
| 部分 SET 的剩余等待 | 约 398–403 ms，关闭后入站额度归零 |
| 新连接读取原值 | 4/4，最后一次旧连接关闭后约 0.83–1.06 ms 完成，首批重连均成功 |
| 同一条热连接 | 22/22 GET 成功 |

本机另三轮也通过，满槽关闭表现为 EOF 或连接重置。部分 SET 和过期旧连接上重发的 SET 都未修改缓存。另一次 SET 刻意让写入者不读回包，第二条连接仍读到新值。客户端遇到无回包只能将结果视为未知。配套的 1 MiB 慢读用例实测了出站额度被占用，发送完成、超时或客户端断开后均归零。

默认配置用两条连接冒烟。一条每约 200 ms GET，75/75 读到已确认的值；另一条闲置约 15.4 s 后再发 SET，收到连接重置。新连接约 1.4 ms 内读到原值。该耗时来自本机回环。保持现有期限和资源上限，接入侧负责回收失效连接并控制重连并发。

```sh
GOWORK=off go test -race -count=3 -v ./internal/server \
    -run '^(TestTCPIdlePoolReclaimsSlots|TestLargeTCPReplyReturnsOutboundBudget)$'
```

## 短状态回复的分配

基线 `c82438a` 以 `io.WriteString` 把固定状态字符串写进 TCP 连接。借用版将状态追加到同一连接原有的 32 B 回复缓冲，再同步写出。当前最长的状态行含换行占 12 B。每条回复仍有原来的完整写期限，普通值回复沿用原发送方式。

复用容量回放。`status` 为约一半未命中 `GET`、四分之一空值覆盖和四分之一已存在键的空值 `SET NX`。空值把短回复的成本和非空入站值缓冲分开。`hit` 全是命中并返回 512 B 值。两种负载均使用 96 条连接、250 µs 节拍，计划每秒 30,000 次普通请求和 40 次背景请求，各做三对 6 秒回放。Linux arm64、Go 1.27.3，服务与驱动分别固定 CPU 0–1、2–5，服务上限 160 MiB。

在预热并建立全部连接后、回放完成后两次采样 `/runtime`。堆字节增量按完整回复数归一。分配次数包括已计入普通堆对象的分配块，以及复用这些块的微小分配，按每千个完整回复归一。采样包含服务进程背景活动和诊断开销。 [Go 运行时计数](https://pkg.go.dev/runtime/metrics) · [Go 分配计数校验](https://github.com/golang/go/blob/go1.27.3/src/runtime/metrics_test.go#L191-L200)

| 指标，三轮中位数 | 短状态基线 / 借用 | 带值 GET 基线 / 借用 |
| --- | ---: | ---: |
| 服务堆分配 B / 回复 | 8.067 / 0.032 | 0.010 / 0.015 |
| 服务堆分配次数 / 千个回复 | 1,001.18 / 0.70 | 0.16 / 0.31 |
| 普通连接计划发送至读完 P99 | 3.47 / 3.45 ms | 3.41 / 3.43 ms |
| 普通连接 RTT P99 | 0.97 / 0.85 ms | 0.95 / 0.72 ms |

12 轮已发送的请求全数收到预期回复，计划完成率最低 99.77%。短状态组每对少分配约 7.94–9.48 B / 回复，分配次数从各轮约每回复一次降到每千次回复少于一次。带值 GET 的分配保持在诊断底噪附近。短状态 RTT P99 配对变化为 +0.229、−0.174、−0.355 ms，服务 CPU 也有升有降。

**采用回复缓冲复用。** 真实 TCP 的管线测试覆盖状态与值完整交错、`EXISTS`、`NO_SPACE` 和出站 `BUSY` 后正常读写，以及入站 `BUSY`、`BAD_REQUEST`、`TOO_LARGE` 后关闭。另用阻塞的连接验证短回复写超时会关闭连接，后续写入未执行。采用依据是短状态的可重复分配收益。

从组件目录复跑，每对可交换两个 peer 的顺序。基线复用当前的测试诊断代码，以取得相同的堆分配计数。

## 连接保留的键缓冲

用 32 条真实 TCP 连接，比较 `61e2872` 和按需分配。每组从全部连接已开始等待请求但还未收到帧开始，随后全部读 1 B 键、其中 4 条读一次上限长度的键后全部回到短键，最后全部重复读上限长度的键。每个阶段用 GC 后的 `HeapAlloc` 减去连接建立前的基准再除以连接数。样本包含同进程客户端和测试连接的开销。Linux arm64、Go 1.27.3，两个版本在 CPU 6–7 串行交错，容器上限 160 MiB。

| 键长上限 | 空闲 B / 连接 | 只读短键 | 偶尔长键后 | 持续长键后 |
| --- | ---: | ---: | ---: | ---: |
| 1 KiB | 3,366 / 2,337 | 3,380 / 2,485 | 3,383 / 2,628 | 3,383 / 3,396 |
| 64 KiB | 67,600 / 1,847 | 67,592 / 1,975 | 67,592 / 10,151 | 67,592 / 67,383 |

表中为基线 / 按需的三轮中位数。64 KiB 上限时，短键组的堆增量减少约 97%，4 条连接用过长键的组减少约 85%。每条连接都用过上限长度时，两版保留量接近。

单连接预热后连续 GET 做五对 TCP 测量，双方四种配置均显示 0 B/请求、0 次分配。1 KiB 上限下，读短键的中位数为 3.46 / 3.40 µs，读 1 KiB 键为 3.66 / 3.66 µs。64 KiB 上限下，读短键为 3.38 / 3.46 µs，读 64 KiB 键为 13.57 / 13.48 µs。配对差异都在 4% 以内。采用依据是空闲和短键连接的堆收益。TCP 回归覆盖上限长度二进制键、短长键管线切换、重连后读回已发布的键、超限关闭以及部分长键归还入站额度。

从组件目录用同一基准代码复跑，比较基线和当前版本。

```sh

git -C .. archive 61e2872 minikv | tar -x -C "$base"
cp internal/server/key_buffer_bench_test.go "$base/minikv/internal/server/"
```
