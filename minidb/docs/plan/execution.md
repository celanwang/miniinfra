# 会话与 SQL 执行

一个连接对应一个会话。会话持有当前事务和请求状态。执行器向事务管理器申请语句快照，再把同一份快照传给扫描、过滤、索引回表和联接。网络回包、客户端取消与数据库提交是三个独立事件。

## 一笔订单经过哪些接口

| 请求 | 执行器与内核的交接 | 客户端看到什么 |
| --- | --- | --- |
| 插入带唯一请求号的订单 | 绑定表和索引，交给写入路径仲裁唯一键。 | 语句成功或唯一冲突。提交前仍可整笔回滚。 |
| 条件扣减库存 | 走主键索引定位候选。写锁等待结束后重查同一行的库存条件。 | 返回受影响行数。零行也是正常 SQL 结果，由订单应用决定回滚。 |
| 查询订单和明细 | 主键扫描、二级索引回表和联接都用本语句的视图，叠加本事务先前的写入。 | 同一查询只能看到整笔订单的一个已发布状态。 |
| 提交订单 | 把提交交给事务管理器，等待发布，再通过连接返回。 | 已提交、已中止，或断线导致结果未知。 |

端到端验收只需要建表及主键、唯一索引、显式事务、插入、条件更新和等值联接。顺序扫描与索引扫描应返回相同的可见行。若列类型或表达式尚不能执行，在规划时返回明确错误。查询计划不应改变事务可见性。 [PostgreSQL 的更新计数](https://www.postgresql.org/docs/current/sql-update.html#SQL-UPDATE-OUTPUTS)

## 断线与重试

服务端在执行 SQL 的同时继续读取 TCP。普通 EOF 允许客户端关闭写方向后继续读取最后一条回应。服务端处理完已收到的请求后结束会话。Go 驱动因取消而中止已在途的请求时，尝试用 TCP reset 关闭连接。服务端读到传输错误后取消会话上下文，等待行锁的语句随即醒来，由原执行线程回滚未提交的更改并释放锁。若服务端只收到 FIN，或网络故障尚未被感知，锁等待和语句超时仍是执行边界。

| 客户端遇到的情况 | 事务状态与客户端动作 |
| --- | --- |
| 语句发送前已取消 | 该语句未执行。若只取消语句自身的上下文，已有显式事务仍可继续。取消 `BeginTx` 使用的上下文时，由 `database/sql` 结束事务。 |
| 显式事务内取消正在收发的语句，尚未发出 `COMMIT` | 驱动返回 `context.Canceled` 或 `context.DeadlineExceeded` 并丢弃连接。结束原事务，从连接池重新获取会话，通过原请求号重试整笔订单。 |
| 可能已发出 `COMMIT` 或自动提交写入，请求未收到有效回包 | 驱动返回 `client.CommitUnknown`。持久化路径已接手的提交由内核完成裁决。驱动将结果留给应用核对，避免 `database/sql` 自动重放写入。 |

用原请求号和摘要核对未知结果。查到同一请求号和摘要时复用结果，摘要不同则报告冲突。若暂时查不到，仍用原请求号重试，让唯一键裁决与原事务的竞争。订单行、扣减和明细在同一事务提交，唯一键冲突后回滚本次尝试。

### 并发订单验证

A 锁住商品 1。B 插入带唯一请求号的订单和一条明细，预占商品 2，随后等待 A。取消 B 的等待语句，记录应用返回错误和另一客户端 C 在商品 2 上完成更新的时间。A 保持原锁到 C 完成。另一个连接同时完成商品 3 的同步更新。

Apple M4 Max 本机 TCP 下，带竞态检测，基线 `934686e` 加探针跑三轮。取消到 B 返回为 73–93 µs，取消到 C 完成更新为 4.910–4.912 秒，接近五秒锁等待上限。修复后八轮分别为 62–142 µs 和 257–650 µs。商品 3 的同步更新用 5.6–12.5 ms。确认 B 的订单及明细不可见、两件库存均未扣减后，从 B 的原连接池重试。从发出取消到收到重试成功用时 7.8–19.0 ms。这些是该测试的观测值。

故障代理分别在转发 `COMMIT` 前、在服务端返回成功后截断连接。两次都会在客户端得到 `CommitUnknown`。第一次原盘重启后没有订单，可用原请求号重新提交。第二次按主键、唯一索引和联接都查到同一笔订单，重复请求号被拒绝。另在服务端已确认自动提交后取消客户端上下文，库存只扣减一次。同一组测试里，96 条真实 TCP 连接在发送最后一条建表请求后关闭写方向，每条均先读到成功回包，再读到 EOF。

```sh
GOWORK=off go test -race -count=3 -v ./cmd/minidbd \
  -run '^Test(Canceled|DeadlineWhileWaiting|UnknownCommit|AutocommitLost|OrderSurvivesLost|TCPHalfClose)'
```

## 当前 SQL 边界

会话执行显式事务或逐语句自动提交。执行错误会回滚显式事务并阻止后续语句转成自动提交，直到应用结束失败的事务。条件更新影响零行时由应用选择回滚。

当前切片支持整型、文本和布尔值。建表在自动提交模式下执行，主键、唯一键及普通二级索引随表声明。更新和删除需要完整主键等值条件，查询可用全表扫描、索引等值查找、过滤和内联接。外键、任意谓词更新、独立索引构建以及 SQL 方言兼容仍待验证。

TCP 服务给每个连接分配一个独立会话，Go 客户端通过标准库连接池接入。成功回包在事务发布之后发送。客户端在可能提交的请求发出后遇到传输中断时返回结果未知，保留由应用用唯一请求号核对的机会。

## 取消只读扫描

SQL 执行器把语句上下文传给堆扫描和索引等值查找。扫描在申请表读锁前后各检查一次取消。持锁时，每页堆扫描和每 128 个索引候选再检查一次。取消后丢弃已物化的行并释放读锁，语句返回时释放原快照。已经排队等表锁的扫描会在取得锁后退出。

每条语句内部共用一份 READ COMMITTED 快照，组装结果时应用 10,000 行上限。回收可能把末页尾部的可见版本搬进已扫描页的空位，按页释放读锁后从旧槽位继续扫描会漏行。因此扫描仍在一次持锁期间遍历物理位置。完成全部扫描的查询仍需物化候选行。取消检查限制的是已取消查询继续占锁的工作量。

### 同表写入测量

在同一张六列订单表填入 12 万或 24 万行。两个请求号列存同样的值，其中一列建索引。两条查询按等值各取最后一行。确认顺序扫描持有读锁后取消客户端请求，等 `database/sql` 返回，再用已开始的事务更新同表另一行。另测空闲写入和提交，把 WAL 刷盘与更新语句耗时分开。探针暂停后台回收线程以定位锁来源，并单独用开启回收的错峰长联接验收并发可见性。

Apple M4 Max、darwin/arm64、`GOMAXPROCS=4`。每个规模在基线和修复版各跑两轮，交错顺序，每轮五次取消。表中为观测范围。快照释放时间由轮询观测，包括采样延迟。

| 表行数 | 取消到快照释放，基线 → 修复 | 客户端取消返回后，同表更新，基线 → 修复 | 无扫描时更新 |
| --- | --- | --- | --- |
| 120,000 | 4.99–8.78 ms → 71–96 µs | 5.03–8.78 ms → 50–94 µs | 61–96 µs |
| 240,000 | 9.66–20.85 ms → 77–100 µs | 9.66–20.89 ms → 51–74 µs | 50–124 µs |

两版客户端均在约 15–40 µs 返回取消错误。基线同表更新的延迟在执行阶段出现，早于提交。修复后的更新耗时回到空闲对照的量级，后续同步提交仍单独刷盘。扫描取消后，连接池可以继续查询并得到与索引对照相同的结果。

基线的引擎直接探针测得，无争用的堆扫描与物化在 12 万行上用时 4.88–10.90 ms，分配约 37.6 MiB。24 万行上用时 9.54–15.69 ms，分配约 75.2 MiB。以上耗时包含选择访问路径、判断可见性和克隆行，申请读锁本身在样本里不到 1 µs。索引对照只物化一行，分配 248 字节。通过 TCP 完整执行时，24 万行的顺序扫描中位数为 27.91 → 27.12 ms，索引对照为 94 → 84 µs。完整扫描的分配量一致，完整查询耗时的样本范围大体重合。

基线提交 `395bdfa` 包含探针。在各版本的 `minidb/` 目录构建二进制，交错执行。将行数换为 `240000` 可复跑大档。

```sh
GOWORK=off go test -c -o /tmp/minidb-scan ./internal/engine
MINIDB_SCAN_LOAD=120000 GOMAXPROCS=4 /tmp/minidb-scan \
  -test.run '^TestTCPSelectiveScanCancellation$' -test.count=1 -test.v
```

## 选择性查询的行复制

单表查询在扫描前绑定 `WHERE`。堆扫描或索引等值查找先检查版本可见性，再用同一个 SQL 谓词判断当前行，只复制匹配的行。表锁内的谓词只比较当前行的列和绑定值。投影和联接继续在表锁外执行，SQL 的 NULL 比较、语句快照和 10,000 行返回上限沿用同一套判断。

### 正常完成的查询

沿用六列订单表，比较无索引的 `external_ref >= ? and status = 'reserved'`，让它匹配最后 1 行或 8,192 行。另测索引等值查找一行作为对照。12 万、24 万行各代表只命中表的一部分，8,192 行档还覆盖整表匹配。每版每档两轮交错执行，每轮分别重复五次。测试使用 Apple M4 Max 本机 TCP，`GOMAXPROCS=4`，并暂停回收线程以隔离表锁成本。

下表为中位数。分配统计包含无并发写入时服务端与客户端同进程处理、传输及完整读取结果的分配。表锁计时从探针首次观测到持锁开始。同表写入在另一组查询中开始于观测到读锁之后，分别计时更新语句和 WAL 提交。

| 表行数 / 返回行数 | 分配，基线 → 改后 | 表读锁，ms | 同表更新，ms | 读取完整结果，ms |
| --- | --- | --- | --- | --- |
| 120,000 / 1 | 59.60 MiB → 5.8 KiB | 8.28 → 1.12 | 5.20 → 1.15 | 14.16 → 1.23 |
| 120,000 / 8,192 | 65.34 → 9.43 MiB | 7.90 → 1.53 | 6.43 → 1.85 | 18.44 → 7.34 |
| 240,000 / 1 | 119.23 MiB → 6.0 KiB | 14.76 → 3.13 | 10.57 → 3.23 | 27.98 → 3.24 |
| 240,000 / 8,192 | 124.94 → 9.43 MiB | 20.74 → 3.94 | 9.55 → 3.71 | 35.43 → 9.50 |
| 8,192 / 1 | 3.71 MiB → 6.5 KiB | 0.29 → 0.05 | 0.31 → 0.09 | 0.99 → 0.14 |
| 8,192 / 8,192 | 9.43 → 9.41 MiB | 0.38 → 0.46 | 0.56 → 0.61 | 6.21 → 6.29 |

索引对照的中位响应在 0.086–0.104 ms。普通写入的 WAL 提交中位耗时在 3.8–4.5 ms。24 万行档返回一行时，同表更新的观测范围从 8.74–20.10 ms 缩到 2.59–4.52 ms。有同表写入时，这一档读取完整结果的中位数从 23.98 ms 降到 3.30 ms。

整表匹配仍要复制每行，而且比较工作现在在表锁内，观察到约 78 µs 的持锁增量。保留复制前过滤的依据是大表选择性查询的分配和同表写入收益。各档使用整数范围和短文本等值条件，长文本比较和多客户端持续拥塞仍需单独测量。

基线提交 `e0e9450` 包含同一探针。在两版的 `minidb/` 目录分别构建，交错执行，将行数换成 `240000` 和 `8192` 可复跑另外两档。

```sh
GOWORK=off go test -c -o /tmp/minidb-scan ./internal/engine
MINIDB_SCAN_LOAD=120000 GOMAXPROCS=4 /tmp/minidb-scan \
  -test.run '^TestTCPCompletedSelectiveScan$' -test.count=1 -test.v
```
