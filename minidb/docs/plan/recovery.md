# 提交与故障恢复

单节点以本机连续、有效的 WAL 和检查点判定同盘重启后的事务结果。同步复制部署还需要选主协议给出的已提交前缀。每个部署模式的成功响应必须能回溯到自己的确认依据。

## 从刷盘到发布

| 位置 | 谁推进 | 用途 |
| --- | --- | --- |
| 本机持久化位置 | WAL 写入器同步一段连续日志后推进。 | 覆盖某事务的完整提交记录后，可在单机模式发布该事务。 |
| 集群提交位置 | 复制协议按任期和多数派裁决。 | 确定接管者必须保留的前缀。单个副本的刷盘位置可能更靠后。 |
| 已发布视图 | 事务管理器发布达到本模式确认条件的事务。 | 查询取得快照。发布后才释放事务锁并返回成功。 |

多笔事务可以共享一次刷盘，各自对照自己的提交记录结束位置。同步失败时停止确认受影响的写入，保留结果未知的语义，让恢复依据实际日志裁决。数据页写回受预写规则约束，检查点同时保存页恢复起点和事务状态。

## 恢复过程

加载最后一个完整检查点，按连续 WAL 重放。建议在检查点后首次修改某页时记录整页镜像，并在写回该页之前，将覆盖镜像和本次修改的 WAL 同步到盘。遇到撕裂页，先从镜像重建，再重放后续修改。保留旧检查点期间，也要保留它所需的镜像和日志。有效提交边界内有完整提交记录的事务恢复为已提交，其余活动事务的行版本保持不可见。已确认范围内发生损坏时停止并报告。 [WAL 与页写入可靠性](https://www.postgresql.org/docs/current/wal-reliability.html)

**复制接管仍需裁决。** 旧主已本地刷盘、集群尚未提交的一段尾部，可能与新主历史分叉。建议副本只把复制协议确认的前缀应用到可服务的数据库视图。旧主重新加入时先隔离，若页或事务状态含有分叉修改，从共同的可信检查点或新主快照重建，再追赶。只截断日志文件无法撤销已写回的数据页。复制日志如何映射到物理 WAL、可接管检查点覆盖哪个位置，须在承诺节点级接管前确定。 [Raft 的日志提交与选主](https://raft.github.io/raft.pdf)

**验收。** 一组丢弃尚未同步的写入，一组在同步成功后丢弃回包，另一组在检查点写回途中模拟半页写入。核对订单、索引和库存。多节点另测旧主带分叉尾部重入，任何接受查询的节点都只能展示合法历史。

## 当前 WAL 格式

第一版存储切片以一条带长度、头部校验和正文校验的记录保存一笔事务的全部重做数据。完整记录就是提交记录，事务超过单条记录上限时在写入前拒绝。写入器收集排队的事务，通过一次同步推进整个批次，再按日志顺序发布。重启扫描完整记录，丢弃可识别的截断尾部，遇到校验错误则停止并报告。启动时先同步恢复出的有效日志，再开始服务。

## 持久化页与检查点

`CHECKPOINT` 排到 WAL 写入器中。前序事务先完成同步和发布，后续提交等检查点操作结束。检查点扫描该发布序号下的可见行。仍在执行的事务可以继续写私有版本，稍后提交的事务从新 WAL 的尾部重放。

每次检查点将目录和已提交行写入新的 4 KiB 页，页包含序号和校验和，文件头保存覆盖的 WAL 位置、发布序号和最大行标识。先同步暂存文件，再原子替换 `minidb.pages` 并同步目录。完成发布后才用空 WAL 回收已覆盖的记录。新 WAL 的头部保存旧日志结尾的逻辑位置，替换后还要同步目录再继续受理提交。

原盘启动只加载已发布的页文件，并从检查点位置重放。停在发布前时，旧页和 WAL 仍在。停在发布后、回收前时，新页与旧 WAL 可组合恢复，已覆盖的记录直接跳过。检查点已经同步后，旧 WAL 和新 WAL 都能支持重启。已发布页文件缺失或损坏时，轮转后的 WAL 不足以单独恢复，启动报错。

此实现以新页文件替换旧一代，部分页写入留在未发布文件。开启原地刷页后才需要前文描述的整页镜像恢复。索引在启动时从持久化行重建。全量检查点期间提交会暂停，RTO、增量刷页、归档和多节点接管仍需独立验证。

验收使用真实服务生成的页文件和 WAL 构造断电后的磁盘状态，分别保留未发布的半页文件和已发布新页配旧 WAL。重启后通过 TCP 按主键、唯一请求号和联接核对同一笔订单，再执行一次检查点验证暂存文件能够清理。

在线回收只清理内存里的旧版本，检查点和 WAL 格式沿用原设计。检查点复制发布视图期间暂停堆槽移动，活跃事务可以继续添加私有版本，提交由 WAL 屏障排在检查点之后。

## 持续短事务下的检查点

四条真实 TCP 连接各执行 40 笔短事务，更新不同主键。热身后在另一条连接发出一次 `CHECKPOINT`，与同负载无检查点交错执行。Apple M4 Max、darwin/arm64、`GOMAXPROCS=4`，每个条件两轮。更新和 `COMMIT` 分开计时。WAL 排队从提交请求尝试入队算到该批次开始写 WAL。检查点计时从进入 WAL 写入器算到轮换结束，分开记录快照扫描与编码、写暂存文件、同步并发布页文件、轮换 WAL。

| 表行数 / 是否检查点 | 更新 P99，ms | COMMIT P99，ms | WAL 排队 P99，ms | WAL 刷盘 P99，ms |
| --- | --- | --- | --- | --- |
| 12,000 / 无 | 0.20–0.52 | 8.47–8.89 | 3.96–4.72 | 4.77–4.86 |
| 12,000 / 有 | 0.46–0.60 | 34.66–34.73 | 30.54–30.68 | 4.88–6.93 |
| 120,000 / 无 | 0.45–0.50 | 8.75–9.93 | 4.58–4.92 | 4.75–5.00 |
| 120,000 / 有 | 0.15–0.42 | 111.70–111.84 | 107.10–107.11 | 4.95 |

以上是逐页写入版。在有检查点的轮次，四笔提交的排队区间跨过 WAL 屏障。屏障内完成的更新用时 62–87 µs。12 万行时，检查点等待前一批提交约 3.6 ms，然后在写入器内占用约 104 ms。扫描、检查可见性、编码和组页占 63–64 ms，写暂存文件占 20–21 ms，发布页文件占 9–10 ms，WAL 轮换占 9–11 ms。缓存写和发布时的同步分别计量。回收互斥等待在这组样本里低于 1 µs。普通提交的新增等待主要发生在写入器队列。

测试完成并关闭连接后在同目录重启，计量到 TCP 监听就绪。12,000 行时，无检查点为 33–39 ms，有检查点为 29–43 ms。120,000 行时，无检查点重放约 31.3 MB WAL，用时 189–200 ms。有检查点读取约 28.0 MB 页及约 41 KB WAL，用时约 220 ms。这里包含恢复时重建索引，磁盘缓存可能仍有数据。各轮重启后逐个核实四个主键都收到完整的 40 次更新，并按唯一索引读取未修改的订单。

### 并发恢复验收

`TestOrderSurvivesLostReplyAndAbruptRestart` 覆盖提交后丢回包。`TestUnknownCommitCanRecoverWithoutOrder` 覆盖提交未转发。`TestOrderSurvivesCheckpointPowerLoss` 用真实文件复现暂存文件的半页写入，以及新页已发布而旧 WAL 尚未回收。`TestQueuedCommitsStayOnTheirSideOfCheckpoint` 核对屏障前后的 WAL 顺序。

`TestConcurrentOrdersRecoverAcrossCheckpoint` 让三笔订单跨过同一次检查点。一笔已持久化，代理仍扣着成功回包，随后丢弃回包。一笔在检查点后提交并收到成功。第三笔在进程被杀时仍未提交。原盘重启后按唯一请求号与主键联接核对，前两笔各自完整保存订单、两条明细和两件库存扣减。未提交订单、明细和扣减均不可见。用结果未知的原请求号重试会遇到唯一键冲突。

### 合并暂存页写入

用 64 KiB 缓冲合并暂存文件的数据页写入。写完最后一页后先排空缓冲，再写文件头。随后同步文件、原子替换、同步目录，最后轮换 WAL。编码或排空缓冲失败时，已发布的检查点仍可使用。

两版按两个数据量交错复跑，各两轮。用同机共享磁盘基准锁错开 MiniMQ，运行期间轮询已知的 MiniKV、MiniMQ 进程。早期同机 I/O 争用样本未纳入下表。

| 表行数 | 页文件写调用，逐页 → 缓冲 | 页文件写入，ms | WAL 屏障占用，ms | COMMIT P99，ms |
| --- | --- | --- | --- | --- |
| 12,000 | 676 → 44 | 2.22–2.31 → 0.33–0.37 | 26.93–28.02 → 25.01–25.12 | 34.77–35.75 → 32.55–32.80 |
| 120,000 | 6,832 → 428 | 19.19–19.47 → 3.35–3.49 | 98.52–103.41 → 84.37–87.49 | 106.16–110.72 → 91.80–95.70 |

大档仍有 64–65 ms 用在扫描和编码。小档缓冲版有一轮更新 P99 为 3.94 ms，该轮屏障内观察到的更新耗时低于 0.09 ms。这个离群值的来源未定位。合并写入的收益集中在暂存文件写入和提交排队。

用旧、新两版分别从同一份 2,500 行 WAL 生成检查点。生成的页文件和轮转 WAL 逐字节相同。交叉打开两版生成的页与 WAL，分别追加已确认写入。原版本再次启动后，均通过主键和唯一键读到附加写入。检查点的文件格式和同步边界沿用逐页版。

逐页版测量提交为 `e92377e`。在两版的 `minidb/` 目录分别构建，换成 `control` 复跑无检查点，换成 `12000` 复跑小档。

```sh
GOWORK=off go test -c -o /tmp/minidb-checkpoint ./internal/engine
MINIDB_CHECKPOINT_ROWS=120000 GOMAXPROCS=4 /tmp/minidb-checkpoint \
  -test.run '^TestTCPCheckpointLoad$/^checkpoint$' -test.count=1 -test.v
```
