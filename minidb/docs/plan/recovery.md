# 提交与故障恢复

单节点以本机连续、有效的 WAL 和检查点判定同盘重启后的事务结果。同步复制部署还需要选主协议给出的已提交前缀。每个部署模式的成功响应必须能回溯到自己的确认依据。

## 从刷盘到发布

| 位置 | 谁推进 | 用途 |
| --- | --- | --- |
| 本机持久化位置 | WAL 写入器同步一段连续日志后推进。 | 覆盖某事务的完整提交记录后，可在单机模式发布该事务。 |
| 集群提交位置 | 复制协议按任期和多数派裁决。 | 确定接管者必须保留的前缀。单个副本的刷盘位置可能更靠后。 |
| 已发布视图 | 事务管理器发布达到本模式确认条件的事务。 | 查询取得快照。发布后才释放事务锁并返回成功。 |

多笔事务可以共享一次刷盘，各自对照自己的提交记录结束位置。同步失败时停止确认受影响的写入，保留结果未知的语义，让恢复依据实际日志裁决。数据页写回受预写规则约束，检查点同时保存页恢复起点和事务状态。

## 恢复过程

加载最后一个完整检查点，按连续 WAL 重放。建议在检查点后首次修改某页时记录整页镜像，并在写回该页之前，将覆盖镜像和本次修改的 WAL 同步到盘。遇到撕裂页，先从镜像重建，再重放后续修改。保留旧检查点期间，也要保留它所需的镜像和日志。有效提交边界内有完整提交记录的事务恢复为已提交，其余活动事务的行版本保持不可见。已确认范围内发生损坏时停止并报告。 [WAL 与页写入可靠性](https://www.postgresql.org/docs/current/wal-reliability.html)

**复制接管仍需裁决。** 旧主已本地刷盘、集群尚未提交的一段尾部，可能与新主历史分叉。建议副本只把复制协议确认的前缀应用到可服务的数据库视图。旧主重新加入时先隔离，若页或事务状态含有分叉修改，从共同的可信检查点或新主快照重建，再追赶。只截断日志文件无法撤销已写回的数据页。复制日志如何映射到物理 WAL、可接管检查点覆盖哪个位置，须在承诺节点级接管前确定。 [Raft 的日志提交与选主](https://raft.github.io/raft.pdf)

**验收。** 一组丢弃尚未同步的写入，一组在同步成功后丢弃回包，另一组在检查点写回途中模拟半页写入。核对订单、索引和库存。多节点另测旧主带分叉尾部重入，任何接受查询的节点都只能展示合法历史。
