# 行版本与索引

堆页保存行版本，B+ 树保存从索引键到候选版本的映射。事务管理器解释版本的可见性。索引扫描、全表扫描和联接读取同一版本时必须作出相同判断。

## 行与版本怎样定位

**建议评审的布局。** 分开保存表内稳定的行标识和物理版本地址。更新沿用行标识，插入分配新标识。版本保存创建事务、使其失效的事务及版本间的联系。物理地址可以随新版本改变。若复用页槽，须在回收旧引用后复用，或用代次识别失效地址。

| 路径 | 读取或维护的状态 |
| --- | --- |
| 按邮箱查用户 | 按规范化索引键找到候选版本，回堆表校验键和快照可见性。旧快照仍能通过旧邮箱查到旧行。 |
| 等锁后更新 | 锁键使用表和行标识。取得锁后，从该行的版本链定位当前有效版本，复查条件。 |
| 清理旧版本 | 事务管理器给出仍在使用的最旧视图。先确认版本已无人可见、执行器或等待者也不会再引用，然后清理索引引用并回收槽位。 |

**需要决定。** A 扫描到一行后等待。B 删除它，C 又插入同主键的新行。建议 A 按原行身份重查，原行已删除即跳过。C 得到新的行标识。可以用版本链追踪或单独的行头目录定位版本。应先固定上述行为，再决定是否付出维护目录的写入成本。

## 页与恢复日志的交接

堆页和索引页都带页号、校验信息和最近修改的日志位置。索引分裂涉及的页、父指针以及页分配记录必须可一起恢复到可遍历的结构。前台执行器用短时页锁修改结构，在等待业务行锁前先释放页锁。持久化和检查点顺序见[提交与恢复](recovery.md)。

**验收。** 并发读取旧邮箱、修改唯一邮箱并触发索引分裂，在页写回中途断电。重启后用主键、新旧邮箱和全表扫描交叉核对。另测删除后同键重插，分别观察旧快照、等待者和新查询的结果。

## 当前行定位

堆页和 B+ 树叶子保存在内存中。行头目录按表内稳定的行标识定位版本链。写语句先按快照选出行标识，获得锁后沿原版本链重查。原行已删除时影响零行，同键重插使用新的行标识。表级短锁保护内存中的页和索引结构，行锁等待与刷盘在表锁之外进行。目录和已提交行随检查点写入持久化页。重启从页重建索引，再重放检查点之后的 WAL。在线回收按表轮转，每 10 毫秒让多张表共用最多 128 个检查单位。检查一个槽位消耗一个单位，访问空表也消耗一个单位。每轮至多访问同一张表一次，同一时刻只锁一张表。它摘掉版本链和各索引中的引用，再移动最后一个堆槽填空。索引候选用双向链保存，回收一个版本无需搬移热点键的整条历史。空键和空树页会被清掉，仍有键的稀疏树页留待后续合并。检查点按页号扫描，期间暂停回收和槽位移动。

## 普通事务尾延迟归因

沿用相同的两个客户端和同步提交条件，每轮每客户端 600 次操作，交错执行回收开启与关闭。测试只给普通事务打开计时，分别记录逻辑行锁、唯一键锁、锁管理器互斥锁、表锁、WAL 排队、写入和同步。WAL 排队从提交请求入队前计到开始写批次。批次中的事务共享写入耗时和同步耗时。慢样本按整笔事务排序，再统计最慢 1% 事务在各阶段的耗时。

计时基线为 `50a8550`。初次交错复跑六轮，行锁和唯一键等待均为零，表锁 P99 为 0.54–1.67 µs。最慢 1% 事务的各轮平均 WAL 排队为 4.47–6.89 ms，自身刷盘为 4.48–6.60 ms。普通事务合批率为 0–0.33%。在这组键互不冲突的负载里，普通事务经常等上一批刷盘结束，随后单独刷盘。这次复测的表锁等待仍在微秒级，尾部时间集中在 WAL。

调整后，写入器在一次刷盘完成且还未唤醒提交者时查看队列。若已有请求积压，而下一批只有一笔就绪请求，给刚被唤醒的客户端留一个 200 µs 的合批窗口。空闲写入器直接刷盘，检查点仍是批次边界，成功响应仍在同步与发布之后。

重新编译基线和调整版，使用相同机器、`GOMAXPROCS=4` 和负载，按版本与回收开关交错跑 12 轮，每个组合三轮。

| 回收 | 普通事务 P99，原版 → 调整版 | WAL 排队 P99，原版 → 调整版 | 普通事务合批率，原版 → 调整版 |
| --- | --- | --- | --- |
| 开启 | 11.74–11.98 → 10.31–12.93 ms | 6.01–6.76 → 5.02–6.16 ms | 0 → 37.5%–41.3% |
| 停止 | 12.08–13.11 → 10.32–11.70 ms | 6.62–7.04 → 5.07–6.01 ms | 0 → 32.3%–33.3% |

开启回收时，每轮 900 次提交的 WAL 同步次数从 900 降到 652–675。混合负载整轮中位用时缩短约 24%。自身刷盘 P99 仍有波动，开启回收的总 P99 有一轮超过原版。合批后两客户端更常同时进入下一轮，观察到表锁 P99 升到 30–58 µs（开启回收）和 158–285 µs（停止回收），仍低于 WAL 等待的量级。

## TCP 多表回收

生产基线为 `af9cb7d`，用 `6f4b3aa` 的测试构建基线二进制，用 `f54a09b` 构建共享预算版。测试通过真实 TCP 监听器和 Go 连接池访问内核。四张表持续写入，另有 48 张单行冷表和一张供联接扫描的 2,800 行表。三个客户端更新同一个热点键并交替提交与回滚，另外两个客户端提交各自独立的键。每次事务在四张写入表各更新两次。客户端按 10 ms 节拍发起，处理超期时按实际完成速率记录。

长读用原生联接持有一条语句的快照。观测到快照后启动写入，并通过另一连接执行 `CHECKPOINT`。联接完成后继续写两秒，再停止发起事务。按堆及两个索引都收敛到四表共 12 个当前版本计时。普通事务 P99 从客户端开始事务到收到提交结果，含 TCP 和连接池开销。表计数在各自锁内采样，整体采样期间写入可以继续。

```sh
# 分别在 6f4b3aa 和 f54a09b 的组件目录构建
go test -c -o /tmp/minidb-reclaim-baseline ./internal/engine
go test -c -o /tmp/minidb-reclaim-shared ./internal/engine
# 按 baseline、shared、shared、baseline 顺序串行运行
MINIDB_RECLAIM_LOAD=1 GOMAXPROCS=4 /tmp/minidb-reclaim-baseline \
  -test.run '^TestTCPMixedReclamationLoad$' -test.count=1 -test.v
```

Apple M4 Max、darwin/arm64 上做了先导和交错复跑。先导基线中，快照释放后仍写入时，可回收积压从 5,557 增至 10,937，停写后 11.51 s 收敛。复跑串行执行，轮询观察了同机 MiniMQ 和 MiniKV 的编译产物。带已知 MiniMQ 基准或测试进程重叠的轮次剔出下表，保留一轮原调度和两轮共享预算。主机没有独占，P99 样本用于观察量级。

| --- | --- | --- |
| 长读期间实际更新 / 秒 | 3,118 | 3,089–3,120 |
| 长读结束后实际更新 / 秒 | 3,695 | 3,679–3,720 |
| 快照释放时可回收版本 | 5,434 | 4,806–4,876 |

共享预算在写入仍持续时基本清掉了释放后的积压。它维持每轮 128 个单位的限制，扫过行数少的表后，用剩余预算继续扫描下一张表。活跃快照仍决定历史保留边界。共享版两轮长读各自的堆高点显示，16–28 个旧版本对当时登记的快照可见，另有 4,448–4,660 个已失效版本因全局最老水位而暂缓回收。长快照期间的保留量和大冷表的扫描开销仍是限制。

TCP 验收确认联接跨提交和检查点保持旧视图，同一连接的下一条 `READ COMMITTED` 查询读取新值，闲置事务释放语句快照。停写后，热点回滚的修改保留在已提交计数之外。原身份被删除并以相同主键重插时，等待者影响零行，重复唯一键仍被拒绝。重开原目录后，四张写入表的主键和唯一键读数与每个客户端的成功提交计数一致。WAL 合批、文件格式和恢复顺序沿用基线。

## 错峰语句快照与历史保留

复跑从 `c87d9a4` 开始，`d88ac1d` 增加测试和采样。两条 TCP 联接分别用主键和唯一二级索引进入。第二条在普通客户端确认四次提交后才发起。三个客户端争同一行并交替提交和回滚，两个客户端提交相互独立的键。事务在四张表各更新两次，另设 12 张冷表。联接扫描使用 1,200 行和 2,800 行两档。基准保留真实 SQL 执行和语句快照，刻意放大联接工作量来得到稳定重叠窗口。

每轮校验两条联接各自的跨表读数，穿插检查点，并在语句结束后继续写入 750 ms。重启前验证删除重插后等待者影响零行、相同唯一键仍冲突。原目录重启后再分别按主键和唯一键核对四张写表。测试用相同的 10 ms 回收节拍记录扫描量、回收量和回收步骤的墙钟耗时。步骤耗时含锁等待及与检查点的互斥。

观测分开报告当前版本、私有版本、对任一已登记快照可见的历史、被最老水位额外挡住的历史和可回收版本。版本结构字节估计包含对象、堆槽指针及值和索引链接的切片空间。它不计共享文本、页元数据和分配器取整。Go 堆样本另外记录整个测试进程的上次标记存活量，包含联接、连接池和采样本身。

区间回收在每轮回收起点与快照登记共用一把锁，取得已发布序号和最多 16 个登记序号。已经提交的删除或更新，如果其结束序号在采样之后，就留给下一轮。之后登记的快照，其序号不会早于这次采样。对于已在采样前结束的已提交版本，只有登记快照与版本的可见区间相交才保留。回收时对有序序号做二分，写入路径仍只登记和释放语句快照。超过 16 个登记快照时沿用最老水位。内部调用者若在写事务结束后仍持有能看见自身写入的旧视图，也沿用水位。

私有创建及私有失效继续保留，中止创建继续可收，中止失效继续恢复旧行可见性。行锁等待用原行标识重查，同键重插仍分配新标识。检查点和堆槽移动继续互斥，WAL、文件格式和恢复边界沿用基线。

## 回收步骤与前台停顿

`ce7b1a0` 的默认回收调度每 10 ms 尝试一个有界步骤。墙钟测量从步骤实际开始到返回，另记录计划 tick 到开始的调度延迟。步骤内部拆分检查点互斥量等待、快照和目录准备、表锁等待及持锁。摘除索引、版本链和堆槽的耗时属于持锁时间。各项为墙钟值，可包含线程被调度离开的时间。

隔离探针使用 4,096 个常驻行、一位主键点读者和一位同步提交者。每轮 1.2 秒，读和写分别按 1 ms、5 ms 节拍启动。两位前台调用者各最多额外占一个语句快照。固定 14 个快照时走区间路径，固定 17 个时走最老水位。积压档在快照前后分别更新前半张表，使后台同时遇到可回收版本和被两种水位区别处理的版本。普通读写选取另一半互不冲突的主键，并逐笔记录表锁从开始等待到取得的时间。用同一张表的回收持锁区间与该时段求交，统计具体有多少普通请求与回收重叠。

探针以真实内核事务隔离锁成本。两条错峰 TCP 长联接另外验证真实 SQL 执行、检查点和恢复，并输出单个最慢步骤的阶段拆分。两种探针都只在测试中启用，常规前台调用沿用原来的无计时路径。

Apple M4 Max、darwin/arm64，`GOMAXPROCS=4`。前台探针每种条件各两轮，开关回收交错串行执行。每轮约 1,200 次点读和 240 次同步提交。另跑两轮 TCP 长档。执行前等待已知的同机 MiniMQ、MiniKV 测试退出，运行期间轮询，纳入下表的样本未观察到已知重叠。主机未独占，统计为观测范围。

| 固定快照 / 初始积压 | 读 P99，关闭 → 开启 | 提交 P99，关闭 → 开启 | 回收持锁与前台等锁的最长重叠，读 / 写 |
| --- | --- | --- | --- |
| 14 / 无 | 14–20 → 13–19 µs | 4.44–4.76 → 4.61–4.76 ms | 9.6 / 11.3 µs |
| 17 / 无 | 20–21 → 20–21 µs | 4.72–7.08 → 4.59–6.23 ms | 1.5 / 5.8 µs |
| 14 / 有 | 26–27 → 42–64 µs | 4.56–5.04 → 4.69–7.60 ms | 98 / 97 µs |
| 17 / 有 | 15–37 → 38–66 µs | 4.65–4.84 → 4.70–4.95 ms | 101 / 120 µs |

无积压档每轮扫描约 15,200–15,400 个槽，没有清理候选，持表锁 P99 为 7.8–13.7 µs。该档没有显示稳定的前台 P99 增量。有积压档每轮各清理 6,144 个（区间路径）或 4,096 个（最老水位）候选。持锁 P99 为 62–121 µs，其中实际摘除 P99 为 37–87 µs。回收与普通点读、写入的等待有可重复的微秒级重叠，少数提交的毫秒级波动无法用记录到的重叠解释。

前两轮 TCP 长档的回收墙钟峰值为 9.98 和 11.72 ms。前者含 9.93 ms 检查点互斥等待，表锁累计只持有 9 µs。后者有约 11.67 ms 落在已记录的等锁、准备及持锁区间之外。早期共享主机上观测到的 34 ms 也是整步墙钟样本，缺少同样的阶段记录。

补测两轮 TCP 长档。最慢步骤分别耗时 8.06 和 11.04 ms，前一轮有 8.00 ms 落在已记录区间之外，后一轮有 10.96 ms 在等待检查点互斥量。四轮里，最长单表持锁为 4.05–4.33 ms，都出现在其他步骤。补测两轮的最长持锁均在写入表 `stock_00`，分别为 4.09 和 4.05 ms，其中摘除版本占约 4.09 和 4.05 ms 的墙钟时间。这个区间前台确实可能等表锁。采样分辨不了摘除的 CPU 时间和期间的调度暂停，也没有将这些峰值配对到 TCP 普通事务最慢样本。

保留现有调度和步长。无积压时未发现稳定的 P99 增量，有积压时可归因的点读退化仍为微秒级。缩小单步预算会改变积压消化速度，而同步提交尾部此前主要受 WAL 排队与刷盘影响。后续若真实 TCP 负载中的毫秒级持锁成为可重复的用户停顿，先逐笔配对同表前台等待、回收摘除与 WAL 时段，确认受影响的是哪类请求。

## 行锁和唯一键的等待期限

每次申请逻辑锁时记下数据库等待期限和调用方截止时间中较早的一项。授予锁前先核对取消和截止时刻，申请锁管理器互斥量的时间也算在预算内。锁可立即取得时直接返回。确实需要等待时，若数据库期限先到，才为剩余时间建立定时器。调用方期限不晚于数据库期限时，直接等待其取消信号。第一次阻塞后，即使醒来时发现锁已经由另一事务取得，也继续使用原截止时刻。锁队列、死锁裁决和写入后的唯一性检查沿用原路径。

### 局部取锁和 TCP 订单

Go 1.27.3、Apple M4 Max、`GOMAXPROCS=4`。对已初始化的锁表用 `context.Background()` 测无争用的新取锁和重复取锁。基线四条路径均为 272 B 和 4 次分配。分配剖析定位到 `context.WithDeadlineCause` 的定时上下文、两个闭包和 `time.newTimer`。改后各路径均为 0 B 和 0 次分配，三轮观测的每次耗时如下。

| 取锁路径 | 基线，ns | 按需定时，ns |
| --- | ---: | ---: |
| 行锁，新取 | 348–391 | 178–249 |
| 行锁，重复 | 237–248 | 127–148 |
| 唯一键，新取 | 247–249 | 155–164 |
| 唯一键，重复 | 201–205 | 116–122 |

真实 TCP 订单包含插入订单和唯一请求号、更新两行带唯一索引的库存、插入两条明细，共 10 次逻辑取锁。无争用档每轮两位客户端提交 280 笔不相交的订单。热点档先由一笔事务持有库存行锁，确认订单进入等待后，让另一笔无关订单先执行并提交，再提交持锁事务。SQL 时间覆盖 `BEGIN` 与 `COMMIT` 之间的写语句。热点第一条更新的往返时间包含等锁，WAL 排队从尝试入队到该批次开始写入，刷盘单独计量。

两版交错各跑三轮，用同机磁盘基准锁错开其他基准，并轮询已知的 MiniKV 和 MiniMQ 进程。无争用档的进程级分配从每笔 394.4–394.7 次降至 342.4–342.6 次，分配字节从 28.5–28.6 KB 降至 24.2–24.6 KB。该统计同时覆盖客户端与服务端。TCP 分配剖析还定位到每条写语句首次建立子上下文时的父上下文 `Done` 通道和子上下文映射分配。因此每单约少 52 次分配，其中 40 次来自取锁定时器相关对象，其余来自四条语句的父上下文。以下为每轮统计量的观测范围。

| 指标 | 基线 | 按需定时 |
| --- | ---: | ---: |
| 无争用订单 SQL 中位，ms | 0.330–0.357 | 0.337–0.357 |
| 无争用订单 COMMIT P99，ms | 8.77–9.66 | 8.74–10.41 |
| 无争用 WAL 排队 P99，ms | 4.68–4.86 | 4.74–4.84 |
| 无争用 WAL 刷盘 P99，ms | 4.81–4.87 | 4.77–4.90 |
| 热点首条更新中位，ms | 14.72–14.74 | 14.64–14.75 |
| 热点期间无关订单 SQL 中位，ms | 0.33–0.40 | 0.32–0.36 |

无争用的 SQL 中位数和同步提交尾部范围有重叠。新版一轮 SQL P99 达到 4.54 ms。双向补测各两轮未再出现该峰值，SQL P99 为 0.86–0.89 ms 和 1.16–1.21 ms。计入补测，整轮进程 CPU 为 180–213 ms 和 203–223 ms。这些样本没有显示进程 CPU 或端到端延迟收益。保留改动的依据是可重复的取锁成本和订单分配下降。热点仍由持锁事务决定，包括持锁者提交的同步时间。

### SQL P99 复验

独立验收用每轮 280 笔订单复测时，逐轮 SQL P99 的中位数由 1.59 ms 升到 2.55 ms。为区分版本影响和同机波动，保持 SQL、两位客户端、`GOMAXPROCS=4` 和数据生成方式，每轮交易数增加到 2,000 笔。两版使用同一份无分段探针的源码 `ce798e6`，A 只用 Go overlay 换回 `bc79470` 的 `internal/engine/locks.go`，B 使用按需定时器。每版各编译一次。只运行无争用子用例。使用同机磁盘基准锁，轮询已知 MiniKV、MiniMQ 进程，有重叠的三轮重跑。

最先连续运行 A/A 和 B/B。SQL P99 分别为 1.764、1.230 ms 和 1.790、1.642 ms，同二进制各差 0.534 ms 和 0.149 ms。随后按 A B B A B A A B 交错运行，四个相邻配对的 B 减 A 差值为 −0.305、−0.179、−0.269 和 −2.415 ms。最后一个配对的 A 为 3.797 ms。汇总 12 轮时，逐轮中位数如下。

| 指标 | A，预建定时器 | B，按需定时器 |
| --- | ---: | ---: |
| SQL 中位，ms | 0.434 | 0.434 |
| SQL P99，ms | 1.659 | 1.416 |
| COMMIT P99，ms | 9.589 | 9.490 |
| WAL 排队 P99，ms | 4.752 | 4.720 |
| 单轮进程 CPU，s | 1.969 | 2.004 |
| 每单进程级分配次数 | 约 399 | 约 347 |

另用可选分段探针各跑两轮，每轮 1,200 笔。按同一笔订单对齐四条 TCP 写语句。服务端计量解码完毕到开始执行的交接、SQL 执行、执行完毕到准备回复。取锁时间是执行的子集。剩余的客户端往返包括驱动、传输、编解码和其他调度等待，探针分辨不了这几项各自的耗时。

| 同一笔 P99 边界订单 | A，两轮范围 | B，两轮范围 |
| --- | ---: | ---: |
| SQL 总计，ms | 1.581–2.044 | 1.157–1.346 |
| 客户端往返剩余部分，ms | 0.971–1.354 | 0.793–1.082 |
| 服务端解码后交接，µs | 51–60 | 97–227 |
| SQL 执行，ms | 0.164–1.019 | 0.133–0.162 |
| 其中取锁，µs | 34–43 | 15–16 |

两边均没有逻辑行锁或唯一键等待。最慢 1% 内，B 的每笔取锁累计最多 19.3 µs。A 有个别超过 3 ms 的取锁墙钟样本，但锁管理器互斥等待的尾组均值低于 1 µs。全进程 Go 可运行队列延迟的 P99 上界约为 49 µs 和 41 µs，无法按此量给单笔订单归因。P99 附近的大段时间主要落在取锁以外。

较长对照未复现早期的候选端尾延迟升高。保留按需定时器的依据仍是每单约 52 次分配的下降。对照结果没有用于承诺端到端加速。
