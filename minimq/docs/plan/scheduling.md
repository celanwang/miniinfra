# 延迟发布、死信与补投

延迟发布改变消息进入历史的时刻。退避只改变某个订阅下一次可领取的时刻。人工补投建立该订阅下的新任务实例。这三种操作可以复用按时间检索的内存索引，但各自的持久状态和副作用不同。

## 到期发布

调度项以其持久 ID 定位正文、最早发布时间和受保护订阅。按时间排序的到期索引由分区状态重建。计时器只提出候选。分区再次检查项是否仍待发布，再在同一命令中指定分配的历史位点、建立任务并结清调度项。批次限制同时考虑条数和正文大小，为普通发布留出执行机会。到期提交前后都可以掉电，恢复后该调度项最多产生一个历史位点。

守护进程每 250 毫秒处理一批到期发布和一批过期租约。若发布批可能已触及条数或字节上限，完成常规轮次后让出 100 毫秒，再补跑至多一批到期发布。过期租约继续由常规轮次处理。补跑沿用同一批次上限和持久提交规则。保留常规节拍可以让普通操作和重试在大批消息同刻到期时继续推进。

## 已经越过消费窗口的补投

**建议评审的实现。** 原订阅已推进到 900，操作者补投来源于 418 的死信时，为新实例建立独立的待领取记录。它的主键是任务实例 ID，418 仅作来源信息。普通投递沿订阅窗口选取，补投从待领取记录选取，两者共用领取凭证、ACK 和退避的裁决规则。调度按补投限速和两类任务的字节预算取数，避免积压补投耗尽在线领取额度。

检查原死信仍可读、操作 ID 的回执和容量后，在一次提交中建立新记录、保存可独立恢复的正文或引用，并登记操作回执。相同操作 ID 的重试复用原实例。建议固定操作 ID 的作用域并对同键异参报冲突。新实例结束时只回收其待领取状态，不移动原订阅边界。原死信自然到期时，新实例继续拥有自己的正文保障。

**验收。** 在原消息段已删除、订阅边界已越过 418 后执行补投，丢掉响应，重启并用原操作 ID 再试。应只有一个新实例，可以被正常领取。随后清理原死信，仍能读到新实例的正文，历史末尾和原订阅边界均不因补投而改变。

单分区实现按订阅限定补投操作 ID 的作用域，回执期沿用去重保留期。每个补投在 WAL 和检查点中保存完整正文。活进程中的补投可以引用源死信的不可变正文，对外读取仍返回独立副本。重开时按记录各自解码。领取提交同时推进该订阅的补投限速时间，基线每批最多加入一条补投，两次补投领取至少相隔 100 毫秒。普通任务可占用该批剩余条数与字节。补投再次耗尽时，新死信带有来源死信 ID。
