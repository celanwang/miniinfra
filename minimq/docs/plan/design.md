# MiniMQ 设计

MiniMQ 是用 Go 构建的持久化消息队列，面向订单通知、Webhook 等可以并行处理、失败后需要核对和重投的业务。一个分区保存一份按发布顺序追加的消息日志。历史读者按位点读取；每个具名任务订阅独立记录一组 worker 的处理进度。增加订阅只增加投递状态，正常投递共享正文。

分段回读沿用 [Kafka 的分区日志思路](https://kafka.apache.org/42/design/design/)；单条领取和超时重投参考 [RocketMQ 的消息级分配](https://rocketmq.apache.org/docs/featureBehavior/08consumerloadbalance/)。选择把首次延迟移出历史日志，是因为长延迟正文可以长期阻塞按前缀清理，[Pulsar 的延迟投递说明](https://pulsar.apache.org/docs/4.0.x/concepts-messaging/#delayed-message-delivery)给出了这种情况。

## 一条延迟订单通知

订单服务在 10:00 提交“订单 731 已发货”，要求 10:15 起投递。通知本身的消息 ID 是生产者生成的 `notice-731-shipped`，路由 key 是订单号。订单号可以有多条通知，每个业务事件使用自己的消息 ID。假设消息进入分区 P2，受理时已有订阅 `notify`。

1. **10:00 受理。** 生产者连同消息 ID、正文和最早发布时间发送请求。分区校验大小、去重记录和可用容量，持久提交调度项，同时登记受保护的订阅和去重回执，再返回消息 ID、分区和“已调度”。此时正文可按 ID 查询调度状态，尚未分配历史位点。成功响应的落盘条件见“提交与恢复”。
2. **10:15 发布。** 到期后，分区在一次提交中向历史日志追加正文、分配位点并结清调度项。假设得到 P2 的位点 418，历史读者现在可以读到它，`notify` 的 worker 也可以领取它。两者均只读已提交且已应用的状态。10:01 到达的普通消息可以先于它取得位点。到期时间是最早发布时间，过载或故障可能推迟实际发布。
3. **worker A 领取。** A 拉取任务，分区持久提交第 1 次领取、凭证和租约截止时间，再交付正文。凭证绑定订阅、分区、任务实例、领取代次和获准的 worker 身份。消息 ID 在重试时保持稳定；位点 418 标识历史位置；一次领取凭证只授权这一次 ACK 或失败报告。领取响应丢失也消耗一次尝试，因为 broker 已授出租约。
4. **成功或重试。** A 调用下游通知服务，并传递稳定的业务幂等键。下游成功后，A 用本次凭证 ACK。有效 ACK 提交后，该任务在 `notify` 中结案。若 A 报告临时失败或租约到期，分区撤销本次领取，记录退避截止时间。退避结束后，同订阅任一获准 worker（包括 A）均可领取，取得新凭证。其他订阅独立处理，历史仍只有位点 418 的一条记录。
5. **转入死信。** 假设最多允许三次领取。连续三次都未获有效确认后，任务停止分配。分区保存可独立读取的死信正文、来源、尝试次数和最后原因，并结清原任务。操作者可以在死信保留期内按订阅和死信 ID 取回它，即使位点 418 所在的日志段已经删除。

普通消息直接执行受理与发布的一次提交。分区数及路由规则在重试期间保持稳定。生产者以同一消息 ID 和相同内容重试，在待调度期间及发布后的约定去重期内返回原回执，同 ID 不同内容或投递时间返回冲突。排队和重试应沿用原定的绝对发布时间。超时表示结果未知；去重期之外，broker 不承诺识别旧请求。去重回执的保留期、历史保留期和死信保留期分别公布。

## 分区保存什么

| 持久数据 | 内容与用途 |
| --- | --- |
| 消息段 | 批次长度、校验和、分区位点、消息 ID 和正文。段内顺序读取，稀疏索引把逻辑位点映射到文件位置，索引可重建。 |
| 调度项 | 延迟正文、最早发布时间、受理时有效的订阅集合。到期发布必须可重放，按时间排序的内存索引可重建。 |
| 订阅状态 | 每分区的连续结案边界、有界窗口内的乱序结案记录、当前租约、累计领取次数和下次可领时间。 |
| 死信与回执 | 死信独立保存完整正文和来源。回执记录生产重试、ACK 和人工补投的裁决，按各自的有效期回收。 |

订阅注册在每个分区单独提交，从该分区注册成功后**受理**的消息开始受保护。注册前已受理、注册后才到期的消息仍按原订阅集合投递。订阅离线期间继续积压；历史读者可以随时加入。这样既能在受理时计算保留和容量责任，也能解释延迟订单究竟会交给谁。

分区为追加、领取、超时和 ACK 排出唯一提交顺序。磁盘同步可合并多个命令，网络可一次传送多条任务，逐条裁决仍然独立。历史拉取按连续批次读取，任务拉取只选已到期且有资格领取的记录。每次拉取同时限制条数与字节数。分区保证日志位置有序，worker 的领取和业务完成可以乱序。

例如 418 等待重试，419 至 425 均已 ACK。订阅保存 418 的状态和后方已结案区间；418 结案后，连续边界直接推进至 426。窗口按它覆盖的**位点跨度**设限，达到上限就暂停向该订阅投递更远的位点。只限制同时工作的 worker 数量无法约束一个旧空洞之后不断增长的已确认区间。固定窗口的代价是某一订阅会因单条长退避任务暂停，新写入与其他订阅仍受分区磁盘配额约束。

## 租约到期与迟到的 ACK

租约以分区权威时间裁决。分区在串行受理命令时固定判定时间，并把决定写入提交序列；副本重放同一决定。有效区间包含起点、不含截止点。即使定时扫描还没运行，已到期的凭证也无法首次确认任务。有效期内被裁决并最终提交的 ACK 可以在到期后才返回给客户端。

沿用位点 418。A 已把通知发出，却在截止时间后才发来 ACK。broker 返回“领取已过期”，原任务继续按到期规则处理。B 若已重领，B 的凭证和状态保持有效。broker 能证明的是**哪次领取得到有效确认**。外部通知可能已送达，死信中的“确认超时”也只表示没有收到有效确认。下游应把稳定幂等键与业务写入原子记录；下游无法判重时，补投前需要核对实际结果。

若 A 的第一次 ACK 已有效提交，仅成功响应丢失，A 在 ACK 回执期内重发同一凭证，会得到“此前已确认”，即便此时已经过期。回执过期且结果无法核实时返回“结果未知”，不修改现有任务。由此可以区分真正的迟到确认和一次成功确认的网络重试。

延迟发布时间、退避时间和租约截止时间都持久化。时间判断要求节点时钟具有已知误差界：只有确定已到期才发布或重领，只有确定仍有效才接受首次 ACK。接管节点先恢复已提交时间下界与任务状态。时钟回拨或误差覆盖截止点时暂停相关判定，直到时间可信。这个选择可能延迟投递或 ACK，换取可解释的截止边界；租约不能阻止旧进程继续操作外部系统。

## 提交与恢复

**单节点。** 分区以带长度、序号和校验的命令批次记录状态变更，批量同步到稳定存储后按序应用。生产成功、领取凭证和 ACK 成功都从已提交且已应用的状态返回。一次到期发布包含调度项 ID、唯一分配的位点及结清动作；一次死信转换同时包含正文来源和原任务终态。重放同一命令不会多发布一次或生成第二条死信。

检查点标明已应用序号，并覆盖保留中的消息段、延迟正文、订阅、死信、回执和容量账目。先写齐并同步数据文件，再原子安装清单并同步目录，随后才可删除已被检查点覆盖的恢复日志。每次恢复从完整清单及其后的连续命令重建索引。未提交的残缺尾批可以丢弃；已提交区间校验失败时停止该分区服务并报告损坏。单机承诺覆盖同盘重启和正确执行同步写的设备掉电，永久丢盘需要备份恢复。

**三副本。** 每个分区使用一个 Raft 组，正文和订阅变更在同一组内提交。Leader 等到多数副本稳定落盘、命令按 Raft 规则提交并在本地应用后才回复。隔离的旧 Leader 无权确认写入、领取或 ACK。历史读由已确认领导权、已应用到读取边界的 Leader 服务。失去多数派时暂停这些服务。

新 Leader 追至已提交边界后接管。有效且未过期的已提交租约继续有效，已确认任务保持结案；切换本身不会给 worker 发第二份凭证。未收到响应的请求仍可能已经提交，按原消息 ID 或原凭证重试。副本快照必须带齐清单引用的所有保留正文和死信，安装完成后才能对外提供读取。Raft 日志满足快照和追赶条件即可截断，业务消息段另按历史承诺和任务引用回收。这带来额外磁盘写入，也使副本恢复与历史留存可以分别验证。

## 死信、历史重读与业务补投

死信以“订阅、原分区位点、任务实例”唯一标识。转换时先确保死信正文可由已提交命令或已同步的死信文件恢复，再原子发布死信索引和原任务终态。转换中断后只允许两种对外结果：原任务仍待转且源正文受保护，或原任务已结案且完整死信可取回。死信保留期从成功转换时起算。

| 操作 | 对系统状态的影响 |
| --- | --- |
| 历史重读 | 读者指定分区和下一位点，自行保存进度。读取、倒回或重复拉取均不授出租约，也不触发通知。位点早于可读起点时返回缺口及当前起点。 |
| 取回死信 | 读取正文、来源和失败原因，无业务副作用。到期清理后返回已不可取回。 |
| 业务补投 | 操作者指定死信、原订阅和幂等操作 ID。分区原子建立拥有正文保障的新任务实例，重置领取次数，记录与旧死信的关系。保留原消息 ID 供业务判重，新实例使用新凭证。补投不追加历史消息，也不重开原任务或其他订阅。 |

补投会实际触发 worker，应显示候选范围、订阅和数量，批量操作限速并逐项返回结果。操作回执期内重复同一请求只返回原结果。死信将在新任务结束前到期时，补投提交必须已经为新任务复制正文或持有独立有效引用。补投与新生产共用正常容量准入，容量不足时原死信仍按原约定可取回。

## 日志回收与磁盘背压

按分区回收连续的已封存日志段。整段超过历史保留期、段内记录对所有受保护订阅均已结案、短时读引用已释放后，才能推进可读起点。持久化新起点及恢复清单后再删除旧文件。历史读者持有的游标不会阻止清理；单次读取有字节上限和期限。长期未完成的 418 可能钉住整段及后面的前缀，即使其中绝大部分任务都已结案。

1. **受理前记账。** 限制单条正文、订阅扇出、尝试次数和同时在途数量。按最坏编码大小为已接受任务计入收尾预算，包括剩余领取及确认记录、各订阅可能产生的死信正文、延迟正文发布期间的双份占用。恢复日志和副本上的物理写入也要计入。按有限窗口分批做检查点和日志截断，为单次切换的临时峰值计费；重复 ACK 等只读回执不重复追加。另在每个存储卷预留有上限的检查点、清单切换及回收工作空间。共享卷上的分区总预算不能超过卷的可用配额。
2. **普通流量不能消耗预留。** 按配额隔离或实际预分配空间，并核对卷剩余字节。接收新正文前，须能同时覆盖此次写入、已有承诺和新增收尾预算；否则在受理前拒绝，返回可重试的容量错误。延迟提交和人工补投同样检查。已确认请求的幂等重试仍可读出原回执。死信保留期内占用正常计费，不能把预计将释放的空间当成现有容量。
3. **优先让已有任务收尾。** 接近上限时暂停新写和非必要后台复制搬迁，为有效 ACK、到期发布、限次重领、死信转换和必要的检查点留出 I/O 与磁盘空间。副本提交所需的复制继续运行。预留随任务终态与物理文件的安全释放结算；退避等待不反复追加计时记录。若未完成任务一直存在，分区可持续拒绝新写，运维可恢复消费者或扩容。
4. **真实写入失败时保留证据。** 外部占盘、设备故障或多数副本不能持久化时，预留也可能不足。ACK 未提交就不能回成功，死信正文未落实就不能推进结案或回收源段。任务保持待确认或待转死信，报告分区、阻塞订阅、最老位点、被钉住的字节和空间缺口。恢复容量后从已提交状态继续。

保守预留会减少同盘可接收的消息量，特别是订阅多、正文大时。它换来一个明确的故障选择：优先兑现已接受任务的承诺。一个待验证的优化是把少量长退避任务的正文与状态原子搬到独立重试区，释放窗口和源段引用。只有在相同容量与故障保证下，正常任务 P99 和被钉字节都有实质下降，且增加的写放大、峰值占用与恢复时间可接受时，才值得采用。

## 故障验证与观察指标

下表是验收条件。每次运行保留生产回执、分区提交序号、领取凭证、ACK 结果以及下游实际执行记录，以便区分 broker 的决定和外部副作用。

| 注入场景 | 必须观察到的结果 |
| --- | --- |
| 延迟受理已落盘但响应丢失，按原 ID 重试；在到期发布前后重启 | 去重期内复用同一调度项。到期前无历史位点，到期后只有一份已发布记录；调度积压能排空。 |
| A 完成业务后租约过期，B 重领，A 迟到 ACK；另测 A 的有效 ACK 仅丢响应 | 前者拒绝且 B 的凭证仍有效，后者在回执期内返回此前结果。单独核对业务实际执行次数。 |
| 三次领取耗尽，在死信提交边界断电或切主 | 恢复后原任务仍受保护或完整死信可取回。源段删除后仍能读取死信；同一操作 ID 补投只产生一个新实例。 |
| 位点 418 长退避，后方连续完成，磁盘压至准入边界 | 窗口状态有界，新写被明确拒绝。预留内的 ACK、死信与回收仍可提交；解除阻塞后可读起点推进。额外制造实际空间不足时不得出现虚假成功。 |
| 单机在批次、检查点和清单切换处掉电；三节点隔离旧 Leader 再切主 | 单机恢复所有已确认批次。集群多数派恢复已提交任务状态，旧 Leader 无成功变更。无多数派时不降低确认标准。 |
| 一边历史回读，一边限速补投，并保持正常生产消费 | 回读不增加领取次数；只有目标订阅获得新实例。核对业务重复、补投剩余数量及在线请求尾延迟。 |

性能分别报告历史读取的字节吞吐、任务领取及 ACK 的条数吞吐，以及生产确认、领取、ACK 的 P50/P99。计量最早发布时间到实际发布的延迟、最老未结任务年龄、重领率、过期 ACK、待转死信数、预留剩余字节、物理可用空间和单机恢复／副本接管耗时。每组结果注明消息大小、订阅数、批大小、持续负载、刷盘和副本条件，并覆盖积压、回收与恢复期间。
